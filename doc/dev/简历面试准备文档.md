## 1. Agent 管道 + 意图路由 + 多模态

### 上下文

RAG 项目常见的做法是用 LangChain 拼一条链：用户输入 → 向量检索 → 拼 prompt → 调 LLM → 返回。这样做的缺点是链路固定、中间状态不可控、出错时很难定位是哪个环节的问题。我们将一次导购对话拆成五个独立阶段，每个阶段有明确的输入输出和错误边界，阶段间通过 `PipelineStages` dataclass 显式传参，各阶段独立 try-catch，可以单独 mock 和测试。

意图识别是这个管道的第一关。常规做法是每次用户发消息都调一次 LLM 来判断意图，但我们发现 80% 以上的用户输入是固定模式——"推荐 XX""换一批""加购物车"——这些用正则和关键词匹配就够用，不需要消耗 token。只有真正模糊的输入（"我想要那种……你懂的"）才走到 LLM。

多模态方面，用户不止打字，可能拍一张护肤品照片问"这个适合敏感肌吗"。图片会先经视觉模型提取品类、品牌、肤质等结构化信息，再与文字描述合并，后续管道不变。同时图片会生成独立的向量，与文本向量两路并行检索。

### 面试追问

**Q: 为什么不用 LangChain？**

LangChain 的 Chain/Agent 抽象适合快速原型，但它的黑盒性导致三个问题：中间状态拿不到（调试只能靠日志）、错误处理不透明（一个环节挂了整个链断掉但不知道哪个环节）、自定义检索策略需要 hack 内部实现（比如我们的硬过滤和向量召回两路并行，用 LangChain 反而更复杂）。3 周比赛时间，与其学框架不如直接写编排代码——我们的 `chat_stream()` 就是一个 async generator，每个阶段 yield 事件，控制流完全透明。

**Q: 80% 的规则命中率是怎么算出来的？真的能覆盖这么多？**

这不是精确统计，是根据我们 4 条 Demo 路径 + 20 条评测样本的实测估算。7 条规则覆盖了"推荐/加购/对比/换一组/预算修改/结算/商业声明提问"七类高频场景。剩下的 20% 是真正的长尾——比如用户上传一张图说"帮我看看这个"，或者用非常口语化的方式表达需求。对于那些，LLM 兜底就够了。

**Q: 管道阶段间怎么传递状态？如果一个阶段失败了，后续阶段会怎样？**

状态通过 `StreamContext` 对象传递，它携带 session_id、turn_id、事件序号生成器、取消令牌、阶段耗时记录。每个阶段独立 try-catch，失败了不会污染后续阶段——比如投机检索失败会打印 warning 然后 `precomputed=None`，后续走串行路径。整个 turn 的顶层有统一的异常处理，任何未捕获异常都会转为 `ErrorEvent` 返回给前端并记录审计日志。

**Q: 图片向量和文本向量怎么做到"并行检索"？**

它们通过 `asyncio.create_task` 分别启动，[retriever.py L162-167](backend/src/services/retriever.py#L162-L167)：文本召回是主路径，图片召回通过 `visual_task = asyncio.create_task(...)` 后台启动。两个任务共享同一套 SQL 硬过滤条件。图片召回即使失败也不会阻塞文本召回——catch 异常后降级为纯文本检索。两个结果通过 `_merge_text_and_visual` 去重合并，文本结果优先排在前面。

## 2. 投机检索

### 上下文

常规的 RAG 流程是串行的：意图识别(1.5s) → LLM 生成检索标准(3s) → 向量化(0.5s) → 数据库检索(1.5s) → Rerank(0.5s)，总计约 7 秒用户才能看到第一张商品卡。但意图识别阶段其实已经拿到了品类、预算、肤质等关键约束——这些信息足以支撑一次检索，没必要等 LLM 把标准"包装"成优美的自然语言。

投机检索的做法是：意图识别一完成，立刻用提取到的约束字段构造一份"简化标准"（纯内存操作），不等 LLM，直接拿这份简化标准启动全量检索。LLM 在后台慢悠悠生成完整标准的同时，检索链路已经在跑了。LLM 完成后，用完整标准对候选做一次轻量筛查（O(n) 内存过滤），对齐两者之间的约束差异。

约束差异主要来自 LLM 的推理能力——比如用户说"推荐洗面奶，不要含酒精的"，意图阶段可能只提取到 `product_type=洗面奶`，但 LLM 能从"不要含酒精的"推理出 `ingredient_avoid=["酒精"]`。后过滤会用完整标准的 7 个硬过滤函数再过一遍，把因缺少额外约束而多召回的候选筛掉。

### 面试追问

**Q: 投机检索的简化标准会不会太粗糙，导致检索结果和最终标准完全不匹配？**

不会完全不匹配，因为核心约束（品类、预算、肤质）是直接从 intent 中复制的。差异主要在 LLM 追加的细粒度约束——品牌排除、成分规避、使用场景。处理方式是后过滤：用完整标准的 7 个 `_FILTER_CHECKS` 对投机结果再做一次筛查，O(n) 纯内存操作。还有一个缓冲设计：投机检索要 top_n=12 而不是最终的 5，即使后过滤筛掉一半还有 6 个候选。

极端情况下（LLM 追加了非常严格的约束导致候选全部被筛光），`precomputed` 会被置为 `None`，自动退化为串行路径——用完整标准重新检索。不会丢功能，只是多等了约 2 秒。

**Q: top_n=12 这个数字是怎么定的？**

经验值。我们实测了几种候选数后发现：12 足以覆盖后过滤的损失（通常筛掉 2-4 个），又不至于让 Rerank 成本过高。`RETRIEVAL_CANDIDATE_MULTIPLIER = 8`，即最终需要 5 个商品时粗排取 top_n * 8 = 40（这个在 [tuning.py](backend/src/config/tuning.py) 里）。投机检索的 12 是更保守的值。

**Q: 为什么不直接用 asyncio.gather 同时启动检索和 LLM，而是先构造 spec_criteria 再分别启动？**

因为检索依赖 CriteriaPayload，而意图识别返回的是 IntentResult——两个数据结构不同。`criteria_from_intent()` 这个纯函数负责把 IntentResult 中的 `extracted_constraints` 字典映射为 `Constraints` Pydantic 对象。这个转换 < 1ms，但它是一个必要的"翻译"步骤。翻译完之后，检索和 LLM 各自拿着自己的 CriteriaPayload 独立运行——投机检索用 spec_criteria，LLM 生成 full_criteria。

## 3. 五层混合检索

### 上下文

纯向量检索（把用户查询和商品文档都转成向量，用余弦相似度排序）在电商导购场景下有致命缺陷：它对"刚性条件"没有感知能力。用户说"200 元以内的洗面奶"，向量检索可能给"198 元的洗面奶"和"300 元的高端洗面奶"打出相近的分数——因为它们在语义上确实都是"洗面奶"。但导购场景下，超预算就是不行。

我们的解法是分层递进——刚性条件放最外层（SQL），语义匹配放中间层（向量 + BM25），精排放内层（Cross-encoder）。每一层只做自己擅长的事，兜底上一层的缺陷。

### 各层详解

**第一层：SQL 硬过滤。** 品类不对、预算超标、用户明确排除的品牌和成分——这些条件可以直接用数据库字段表达，走 B-tree 索引，不经过向量相似度。7 个纯函数组成 `_FILTER_CHECKS` 元组，通过 Python 的 `all()` 串联，短路求值。

**第二层：向量召回。** 用户查询和商品 chunk 都通过 `text-embedding-v3` 转为 1024 维向量，在 pgvector 中用 HNSW 索引做余弦距离排序，召回 Top-200。向量擅长的是"油皮"和"控油"这种概念关联——它们不会在文本中直接相邻出现，但语义上高度相关。

**第三层：BM25 关键词召回。** 向量检索的弱点是专有名词——"兰蔻"和"小黑瓶"在语义上有关联，但向量可能把"理肤泉"也算成近义词。BM25 是经典的词频-逆文档频率算法，基于 jieba 分词后做精确词匹配，保障品牌名、型号等专有名词的召回。

**第四层：RRF 融合 + Cross-encoder 精排。** 向量召回和 BM25 各自返回一个排序列表，但两个列表的分数量级不同——向量分在 0.7-0.99 区间，BM25 分在 0-50 区间。直接加权会导致向量分主导。RRF（Reciprocal Rank Fusion）只关心排名不关心分数，公式是 `score(d) = Σ 1/(k + rank_i(d))`，k=60。融合后再由 Cross-encoder 重新打分——Cross-encoder 同时读 query 和 document，比 Embedding 的"分别编码后算余弦"更精准。

**第五层：渐进式放宽。** 严格条件下无结果时，不对用户说"没找到"，而是逐步放松约束：预算 ×1.3 → ×1.5 → 不设上限。但品类不进入放宽逻辑——品类不对的商品推荐了也没意义。

### 面试追问

**Q: 为什么硬过滤要放第一层，而不是检索完再过滤？**

两个原因。性能上：先硬过滤可以缩小向量搜索的候选范围，pgvector 的 HNSW 索引在候选集小时更精准且更快。逻辑上：如果把硬过滤放在向量检索之后，可能出现"语义最相关的 50 个商品全部超预算"的情况——用户要 200 以内的，结果 Top-50 全是 300+，全被筛掉，召回为空。先硬过滤保证了进入向量检索的都是满足刚性条件的。

**Q: BM25 和向量召回各自适合什么场景？为什么不能只用其中一个？**

向量适合语义关联——"油皮"和"控油"在字面上没有重叠但语义高度相关，BM25 抓不到这种关联。BM25 适合精确匹配——用户说"兰蔻小黑瓶"，向量可能把"兰蔻""小黑瓶"当成两个独立概念分散到不同方向，但 BM25 能精确命中包含这些词的商品。两者互补，融合后效果比任一单路好。这是信息检索领域的基本共识——Dense + Sparse 混合检索。

**Q: RRF 的 k=60 是怎么定的？为什么不直接加权求和？**

k=60 是 RRF 论文的标准推荐值，不是我们调的。直接加权求和的问题是两路分数的量级和分布完全不同——向量分是 cosine distance 转换的 [0,1] 区间，BM25 分取决于文档长度和词频，可能是 0 到几十。要做线性加权需要先做分数归一化，但归一化本身假设了分数分布（比如 min-max 归一化对异常值敏感）。RRF 只依赖排名，完全不需要知道原始分数的分布。

**Q: "200 元预算"的硬过滤是用 `price <= 200` 吗？199 元和 201 元怎么处理？**

对，直截了当的 `price <= budget_max`。199 通过，201 不通过。没有模糊区间——电商导购场景下价格是用户明确表达的约束，不是偏好。但如果严格条件下无结果，会触发渐进式放宽：200 × 1.3 = 260，此时 259 元的商品会进入候选。放宽倍数在 [tuning.py](backend/src/config/tuning.py) 的 `BUDGET_RELAXATION_STEPS` 中配置。

## 4. 防幻觉体系

### 上下文

RAG 能减少幻觉但不能消除幻觉。LLM 在生成推荐文案时会在三个环节编造内容：编造"为什么推荐"的理由（实际数据库里没有）、编造商业承诺（"包邮""有货""支持优惠券"）、编造价格（把 89 元说成 79 元）。

我们的防线按"哪类幻觉在哪层拦截"来设计，不试图用一层解决所有问题。

### 三层详解

**第一层：证据溯源。** 每条推荐理由必须在 `evidence_links` 表中有对应的 chunk 原文——来自商品的营销文案、FAQ 或用户评价。chunk 在入库时按内容类型打上 `evidence_kind` 标签（why_buy/faq/risk/compare），检索阶段按优先级各取一条作为证据。推荐卡片的 `evidence` 字段携带原文 snippet 和 `source_id`（指向具体 chunk），前端可追溯到数据库原文。这意味着 LLM 不能在推荐理由里编造"很多用户说控油效果好"——除非数据库里真的有一条含"控油效果好"的 chunk。

**第二层：禁止词过滤。** LLM 在训练语料中见过大量电商文案，它对"包邮""满减""限时优惠"这类商业承诺的表达非常熟练——但熟练不等于真实。我们维护了一份 23 项禁止词清单（`_FORBIDDEN_COMMERCIAL_TERMS`），LLM 输出的文案如果在禁止词列表中命中，整轮推荐文案会被拒绝并抛出异常。不是替换，不是警告，是拒绝——因为一旦出现商业承诺词汇，说明 LLM 已经开始"编故事"了。

**第三层：价格校验。** GroundingGuard 用正则 `r"(\d+(?:\.\d+)?)\s*(?:元|块|RMB)"` 扫描 LLM 输出中的价格数字，然后和数据库里该商品的实际价格（`base_price` 和所有 SKU 价格）做交叉比对。不匹配时不是拦截整个输出，而是在已有文本后追加一条纠偏标注——因为流式输出可能已经推送给客户端了。

### 面试追问

**Q: 禁止词过滤是 23 项，这个清单怎么维护？新增一项需要改代码吗？**

当前 23 项是硬编码在 `_FORBIDDEN_COMMERCIAL_TERMS` 元组中的。理想方案是配置化——把这 23 项放到 `domain_terms.py` 或一个独立的 yaml 文件里，加载时动态构建过滤集合。比赛阶段因为品类和场景固定，硬编码够用且最快。生产环境会改成配置驱动，并支持不同品类有不同的禁止词——比如数码品类可能需要额外禁止"国行""港版"这类 LLM 倾向编造的版本描述。

**Q: 第二层拦截和第三层校验的顺序有关系吗？为什么价格校验放最后？**

价格校验是最轻量的（只做正则提取+数值比对），但也最"温和"——它只追加纠正标注，不拒绝输出。禁止词过滤更"强硬"——命中直接抛异常。所以顺序是：证据绑定在检索阶段就完成了（和 LLM 无关），禁止词过滤在 LLM 输出后立即执行（先过强校验），价格校验做最后一道兜底。类似安检的逻辑：先查有没有危险品（禁止词），再核验身份信息（价格）。

**Q: 如果 LLM 编造了一个数据库中不存在的价格，你们的纠偏标注是怎么表现的？**

不是静默替换，而是追加标注。比如 LLM 说"仅售 79 元"，但数据库里是 89 元，GroundingGuard 会在文本末尾追加"（注：该商品实际价格为 89 元，以上推荐文案中的价格信息可能存在误差）"。之所以不替换原文，是因为流式输出场景下原文可能已经推给客户端了，追加是唯一不影响已有渲染的方式。

## 5. SSE 流式推送与可靠性

### 上下文

Agent 后端的一个核心挑战是"怎么让用户感觉系统很快"。LLM 调用通常需要 1-3 秒，直接等全部生成完再返回，用户会看到 3 秒的白屏。我们的做法是：(1) 管道启动后立即发 thinking 事件（首字延迟 < 100ms），(2) 每 0.8s 更新一次进度文案，(3) 每个阶段的产出作为独立事件流式推送，不等所有阶段完成。

流式推送带来的副作用是错误处理变复杂——如果已经推了 3 条商品卡然后 LLM 挂了，不能简单地重试整轮对话（客户端会收到重复内容）。另外，前后端的事件协议如果不同步（比如后端加了一个新事件类型但前端还没更新），会导致解析失败。

### 面试追问

**Q: 为什么选 SSE 而不是 WebSocket？**

导购场景的数据流是单向的：后端推事件，客户端接收。WebSocket 的全双工能力用不上。SSE 的优势是原生支持自动重连（浏览器内置）、更简单的服务端实现（就是一个长连接的 HTTP 响应流）、兼容 HTTP/2。而且我们的 Android 端用 OkHttp SSE 直连，不需要额外的 WebSocket 库。

**Q: 心跳 0.8s 一次，为什么是这个频率？**

工程折中。太快（比如 0.2s）会增加带宽消耗和客户端渲染压力，太慢（比如 2s）会让用户感觉"卡住了"。0.8s 接近人对"系统还在工作"的感知下限。技术上 `HEARTBEAT_INTERVAL_SECONDS = 0.8` 在 [pipeline.py L163](backend/src/runtime/pipeline.py#L163) 定义，配合 `asyncio.wait(timeout=0.8)` 实现非阻塞等待。

**Q: Schema 校验在 import 时做，不会拖慢启动速度吗？**

校验只比较事件类型名称的两份列表（JSON Schema 的 `$defs` 和 Python 的 `EVENT_TAG_MAP`），耗时 < 1ms。它不做 full schema validation——那由 `test_sse_events.py` 的单元测试负责。Import 时校验的目的是防止手动改了 Schema 或 Python 端但忘了同步另一端——不一致直接 `ImportError` 阻止启动，比上线后发现好一万倍。

**Q: 流式已推送内容后再失败不重试，那用户看到的错误怎么处理？**

前端收到 error 事件后标注该轮对话为"部分失败"状态。已推送的商品卡保留在聊天流中（因为是真实检索结果），但推荐文案如果中断，前端显示截断文案 + "生成中断"提示。用户可以选择重新发送消息重试整轮。

## 6. 多轮对话与反馈闭环

### 上下文

单轮对话做得好只是及格线。真实使用中用户会连续追问："推荐洗面奶" → "预算降到 200" → "不要含酒精的"。每一轮都不应该让用户重复之前说过的话。同时，用户可能会中途切换话题——聊完洗面奶突然问"有没有手机推荐"——这时候之前的品牌和产品类型约束应该清空，但预算这类通用限制可以保留。

另外，用户的行为反馈（左滑不喜欢、点击喜欢、点开详情）不只影响 UI，应该注入下一轮检索——"不喜欢含酒精的"这条偏好应该持续影响后续所有推荐。

### 核心设计

**约束继承。** `_merge_followup_context()` 逐字段检查本轮是否已设置——已设置的优先（用户刚说的比历史记录重要），未设置的从上一轮复制。比如用户第 1 轮说了"油性肤质"，第 2 轮说"预算降到 200"，第 2 轮的结果会同时包含 `skin_type="油性"` 和 `budget_max=200`。

**话题切换检测。** 从三个维度判定：(1) 品类变了——"美妆护肤" vs "数码电子"，权重最高；(2) 产品类型变了——"洗面奶" vs "手机"，经 normalize 后比对；(3) 本轮新增了品牌偏好但没有产品类型——"推荐 Nike"在之前的护肤品上下文中，暗示话题切换。判定为话题切换后，品牌和产品类型约束清零，预算和场景等通用约束保留。

**反馈注入。** 用户的操作（like/dislike/view_detail）写入 `feedbacks` 表。下一轮检索时，`get_feedback_context(session_id)` 拉取当前会话的所有反馈，提取 `avoid_products`（不喜欢的商品 ID）和 `avoid_traits`（不喜欢的成分/特质），注入 `RetrievalFilters` 中传递给检索器。

### 面试追问

**Q: 话题切换的判断标准中，"三维判定"的具体权重是怎样的？**

没有权重。是三个独立的 if 条件：(1) 品类变了 → 切换；(2) 产品类型变了 → 切换；(3) 本轮有新品牌偏好但没有产品类型 → 切换。满足任意一条即判定为话题切换。这个逻辑在 `_is_topic_switch()` 中，约 25 行代码，不是模型，没有分数。

**Q: 约束继承的优先级——如果用户第 2 轮说"干性肤质"，但第 1 轮设置的是"油性肤质"，以哪个为准？**

本轮优先。`_merge_followup_context()` 中写的是 `if key not in constraints and has_context_value(value)`——只有本轮没有设置该字段时，才从上一轮复制。用户说"干性肤质"，这一轮的 `skin_type` 已经有值了，上一轮的"油性"就不会被继承。这也是为什么"预算降到 200"不用重复"油性肤质"——"预算降到 200"这个输入没有改变 skin_type，它从上一轮继承。

**Q: 反馈闭环和约束继承有什么区别？**

约束继承是"跨轮记住用户说过什么"，反馈闭环是"跨轮记住用户做过什么"。前者处理的是用户显式表达的约束（"预算 200""油性肤质"），后者处理的是用户行为信号（左滑不喜欢某个商品、点击喜欢）。两者的持久化方式也不同：约束通过 `conversations` 表保存，反馈通过 `feedbacks` 表保存。检索时两者合并注入。

**Q: 如果用户在第三轮说"把我刚才不喜欢的那两个也排除掉"，系统怎么处理？**

"刚才不喜欢的"首先会被捕获为一条 feedback 记录（action=dislike, product_id=xxx），写入 `feedbacks` 表。下一轮检索时，`get_feedback_context()` 拉取该 session 的所有 dislike 记录，提取商品 ID 作为 `avoid_products`，传递给检索器。检索器的 `_passes_feedback_product_filter` 会直接排除这些商品。用户不需要记住商品 ID，系统自动维护了一个"已排除列表"。

## 7. 综合追问

### Q: 如果让你重新做这个项目，你会改什么设计决策？

三个。

第一，证据的 `evidence_kind` 应该传递到前端。当前 chunk 入库时打了 why_buy/faq/risk/compare 标签，但序列化到 SSE 的 `EvidencePayload` 时只保留了 snippet 和 source_id，丢失了证据类型。前端只能展示"这是一段引用"，不能区分"这是来自 FAQ 的警告"还是"这是用户好评"。改法很简单——EvidencePayload 加一个 `evidence_kind` 字段。

第二，23 个禁止词应该配置化。当前硬编码在 `_FORBIDDEN_COMMERCIAL_TERMS` 元组里，新增一项要改代码部署。应该在 `domain_terms.py` 或 yaml 配置中维护，支持按品类差异化——数码品类的禁止词和食品品类不同。

第三，投机检索的 spec_criteria 目前是纯确定性映射（直接从 intent.constraints 拷贝），可以用一次轻量 LLM 调用来补充——比如把"油皮"归一化为 `skin_type="油性"` 这种细微转换，确定性映射有时会漏。代价是多 0.5s 延迟，但可以显著提高 spec_criteria 和 full_criteria 的一致性，减少后过滤的筛掉率。

### Q: 你遇到的最难解的 bug 是什么？

百炼 `text-embedding-v3` 的 batch size 限制。代码中有一处批量 embedding 调用的 batch size 设成了 32，但百炼的实际限制是 10。超过 10 会返回 400 错误。问题是这个错误被 fallback 机制静默吞掉了——embedding 调用失败触发了确定性 fallback（返回 16 维伪向量），整个系统看起来"能跑"，但检索效果大幅退化。Debug 的难点在于：系统没有任何报错、日志里只有一条 inconspicuous 的 fallback warning、评测指标也没有明显崩塌（因为 16 维伪向量在小数据集上也有一定区分度）。最后是通过 `smoke_live_rag.py` 的严格模式（`STRICT_RUNTIME=1`，禁用所有确定性 fallback）暴露出来的。教训是：fallback 机制必须有可观测性——每次降级都应该记录原因和影响范围，不能静默。

### Q: 你怎么评估这套系统的效果？怎么证明你的混合检索比纯向量检索好？

搭建了一套评测管道，跑的是完整的 `chat_stream()` 管道而非 mock 单个函数。20 条评测样本覆盖了品类约束、预算场景、礼物场景、反选排除、多轮一致性等 10 种场景类型。

指标分两轨：8 个确定性指标（意图准确率、Recall@5/@10、约束满足率、证据覆盖率等）直接对结构化输出做校验，不需要 LLM；8 个 LLM Judge 指标（Faithfulness、Context Precision、Answer Correctness 等 RAGAS 标准维度）用 Qwen-Plus 做评委打分。

评测结果可以直接对比不同策略版本的效果差异——baseline（纯向量）→ +SQL 硬过滤 → +BM25 → +Rerank → +防幻觉，每个策略跑完 20 条样本后看 Recall@10 和 Faithfulness 的变化趋势。虽然样本量只有 20 条、统计显著性有限，但趋势是一致的：硬过滤和 Rerank 的贡献最大。

## 8. 检索与模型架构追问

### Q: 精排模型具体是什么？是本地部署的还是远端调用的？怎么控制延迟？

精排用的是远端的 `qwen3-rerank`（百炼 API），不是本地部署的 Cross-Encoder。配置在 `llm_profiles.yaml` 中，通过 HTTP POST 调 `/reranks` 端点。代码在 [reranker.py L113-144](backend/src/services/reranker.py#L113-L144)。

它对 SSE 流式体验影响不大，原因有三：①精排发生在粗排之后——候选已经从 200 个缩减到 15-20 个，输入很小；②精排的 ~0.3-0.5s 开销在 criteria_card 到第一张 product_card 之间的过渡中被动画覆盖，用户感知不到；③精排 API 是专用推理端点，不是通用 LLM，对 batch size 15-20 的响应延迟远低于 chat completion。

如果面试官追问"为什么不本地部署"：3 周比赛时间没空搞 GPU 和模型部署，调 API 是最快跑通的方案。

### Q: 如果向量召回和 BM25 召回的结果完全不重叠，融合逻辑怎么处理？

坦诚说——BM25 独有的结果在现版代码中会被丢弃。代码在 [retriever.py L213-231](backend/src/services/retriever.py#L213-L231)：`chunk_by_id` 是从向量召回的 hits 构建的字典，RRF 融合后的 `merged_ids` 中那些 BM25 独有但向量没召回的 ID，在 `chunk_by_id[cid]` 这步拿不到，被跳过了。BM25 实际上只起到"重排向量结果"的排序优化作用，不能独立注入新候选。

实际效果：在小数据集（1292 chunk）上，pgvector 召回 Top-200 覆盖面很广，BM25 独有的情况极少发生。评测数据也验证了这一点——加 BM25 之后的 Recall@10 提升主要是 BM25 把被向量漂移掉的品牌名商品排到了前面，而不是找到了新商品。

改进方向：应该在 RRF 融合后用 BM25 独有结果的 chunk_id 去补查 `product_chunks` 表、还原为 ProductHit 并追加到候选列表中。

### Q: 多路检索时，谁给结果打分？

每一步的打分者不同，接力进行：

- **SQL 硬过滤**：不打分，只做二值判断（通过/不通过）。预算超标直接踢掉，不参与后续排名。
- **向量召回**：pgvector 的余弦距离转相似度分数。打分者是 embedding 模型——它决定了"油皮"和"控油"在向量空间里有多近。
- **BM25 关键词召回**：BM25 算法自身基于词频、逆文档频率和文档长度归一化打分。打分者是 BM25 公式。
- **RRF 融合**：不打原始分，只融合排名。解决向量分（0.7-0.99）和 BM25 分（0-50）量级不可直接比较的问题。公式：`Σ 1/(60 + rank_i)`。
- **粗排加权**：向量分 + 过滤匹配分 + 预算惩罚，三因子排序。代码在 [retriever.py L354-373](backend/src/services/retriever.py#L354-L373)。
- **精排模型**：qwen3-rerank 对粗排后的 ~15 个候选逐一打分。这是唯一同时看到查询和文档内容的打分者，比分别编码后算余弦距离更精准。

接力棒：pgvector → BM25 公式 → RRF 融合排名 → 粗排加权 → qwen3-rerank 最终判决。

### Q: BM25 是什么？和向量检索有什么区别？

BM25 是一种经典的关键词检索算法（TF-IDF 的升级版），基于三个因素打分：词频（搜索词在文档中出现多少次，做了饱和处理避免长文档天然占优）、逆文档频率（这个词在全库中有多稀有，"兰蔻"比"洗面奶"权重高）、文档长度归一化（长文档要做惩罚）。

和向量检索的本质区别：向量靠语义——"油皮"和"控油"这两个词字面不重叠但在向量空间中距离很近。BM25 靠字面——"兰蔻"就是"兰蔻"，不会被上下文理解成别的。两者互补：向量处理概念关联，BM25 保障专有名词不被漏掉。

### Q: 为什么检索要多路并行，而不是串行？

因为三路检索之间没有数据依赖。SQL 硬过滤不依赖向量结果，文本向量和图片向量各自查自己的 pgvector 索引。并行后取最长的那一路（约 1.5s），而不是三路加起来（约 3-4s）。代码在 [retriever.py L162-167](backend/src/services/retriever.py#L162-L167)：`visual_task = asyncio.create_task(...)` 在后台异步跑，主路径继续执行文本向量召回，两者通过 `await` 汇合。

## 9. LLM 调用方式追问

### Q: 这个项目是怎么调 LLM API 的？为什么不用 OpenAI SDK？

用 `httpx.AsyncClient` 直接发 HTTP POST 请求，没用 OpenAI SDK。代码在 [llm_gateway.py](backend/src/services/llm_gateway.py)。

三个原因：①需要自定义重试策略——超时不重试、只重试网络瞬断（`ConnectError`/`RemoteProtocolError`/`ReadError`），SDK 的重试行为是内置的没法精确控制。②项目同时接百炼和 Doubao 两个 provider，每个请求的 base_url 和 api_key 动态配置，直接控 HTTP 层面比依赖 SDK 的统一接口更灵活。③httpx 本来就在项目里给 embedding 和 rerank 发请求用，没必要为了调 LLM 单独引入 openai 包。

代价是自己处理流式 SSE 解析和 HTTP 错误码判断，但 3 周比赛时间有限，能直接掌控的代码比依赖外部库的默认行为更可控。

### Q: LLM、Embedding、Rerank 这三者有什么区别？

虽然都是 AI 模型，但做的是三件完全不同的事：

- **LLM（大语言模型）**：输入文字，输出文字。能理解上下文、做推理和生成。模型是 qwen-turbo、Doubao，调 `/chat/completions` 端点。
- **Embedding（向量模型）**：输入文字/图片，输出一串数字（1024 维向量）。不做对话，不懂上下文，唯一能力是把内容编码为数学坐标，供向量数据库做相似度搜索。模型是 text-embedding-v3（文本）和 qwen3-vl-embedding（图片），调 `/embeddings` 端点。
- **Rerank（排序模型）**：输入"查询 + 文档"对，输出相关性分数。不生成文字也不转向量，只管判断这篇文档和用户查询有多相关。模型是 qwen3-rerank，调 `/reranks` 端点。

类比：LLM 是和客户聊天的前台，Embedding 是把信息编码成坐标的翻译官，Rerank 是给候选文档打分的裁判。三者功能、输入输出格式、API 路径完全不同。

### Q: 整个项目用到了哪些 AI 模型？分别在什么场景用？

五种模型，覆盖五个 API 端点，全部通过 httpx 统一发 HTTP 请求：

| 模型类型 | 模型名 | 调用端点 | 使用场景 |
|----------|--------|---------|---------|
| 对话 LLM | qwen-turbo / qwen-plus / Doubao | `/chat/completions` | 意图识别、标准生成、推荐文案、最终决策、对比旁白、场景策略旁白、评测 LLM Judge（7 个任务） |
| 视觉 LLM | Qwen-VL-Plus | `/chat/completions` | 拍照找货——提取图片中的品类/品牌/肤质/成分 |
| 文本 Embedding | text-embedding-v3 | `/embeddings` | 把用户查询和商品 chunk 转成 1024 维向量 |
| 视觉 Embedding | qwen3-vl-embedding | `/embeddings/multimodal-embedding` | 把用户上传的图片转成向量做视觉相似度搜索 |
| Rerank | qwen3-rerank | `/reranks` | 对粗排候选重新打分排序 |

所有代码入口在 [llm_client.py](backend/src/services/llm_client.py)、[embedding.py](backend/src/services/embedding.py)、[reranker.py](backend/src/services/reranker.py)。
