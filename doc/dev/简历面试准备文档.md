## 2. 项目开场

### 2.1 15 秒版本

> BuyPilot-AI 是一个基于 RAG 的多模态电商导购 Agent。后端把用户的模糊购物需求转换为封闭的 Criteria DSL，再通过 pgvector、BM25/RRF 和 Rerank 找到商品及证据，最后用 SSE 返回可解释的推荐、反馈和决策结果。

### 2.2 1 分钟版本

> 这是字节跳动 AI 全栈挑战赛的三人项目，开发周期三周。我主要准备以后端与 Agent 链路为核心来介绍。系统没有把一次推荐简单写成“检索后调用 LLM”，而是拆成意图、标准、检索、推荐和决策五个阶段。
>
> 用户请求进入 FastAPI 后，Pipeline 先做图片预分析、意图识别和槽位检查，再按 Intent 分发到推荐、对比或购物车 Handler。推荐链路会把自然语言转换成类型受控的 Criteria，并用 Intent 中已经确定的约束提前启动投机检索，使正式 Criteria 的模型生成与检索 I/O 重叠。
>
> 数据侧把 100 件商品加工成 1292 个语义 Chunk，使用 1024 维 Embedding 和 pgvector 做语义召回，再经过确定性过滤、BM25/RRF 排名增强和 Rerank，最终按商品聚合并绑定原始 Chunk 证据。多候选收敛时由确定性评分选择赢家，LLM 只负责解释。系统通过 SSE 流式返回，并建立了多轮状态、反馈、审计、检索 Trace 和离线评测闭环。

### 2.3 可以安全使用的数据口径

| 数据 | 推荐表述 | 注意事项 |
|---|---|---|
| 团队与周期 | 3 人，3 周 | 不夸大个人独立完成整个项目 |
| 商品规模 | 100 件商品，4 个顶层品类 | 当前是比赛数据规模，不代表大规模生产验证 |

## 3. 卖点一：Agent 管道、分层路由与 Criteria DSL

### 3.1 对应简历表达

> 设计五阶段 Agent 管道（意图→标准→检索→推荐→决策），以 Pydantic 模型解耦阶段。采用“确定性规则 + LLM”分层路由，明确指令走规则、模糊表达调模型；将自然语言转换为封闭 Criteria DSL，经归一化、上下文合并和槽位检查后路由。

### 3.2 30 秒回答

> 我们没有让 LLM 直接控制整条业务链，而是把一轮对话拆成 Intent、Criteria、Retrieval、Recommendation 和 Decision 五个阶段。明确的加购、换一组、预算调整等表达先走确定性规则，规则不能可靠判断时才调用 LLM。无论来自规则还是模型，结果都会被约束到 `IntentResult` 和 `CriteriaPayload` 等 Pydantic 模型中，再经过归一化、历史合并、槽位检查和 Handler 分发，因此模型不能随意发明新的动作或检索字段。

### 3.3 完整调用链

```text
POST /chat/stream
→ api.chat.stream_chat()
→ runtime.pipeline.chat_stream()
→ runtime.pipeline._run_chat_turn()
→ runtime.pipeline._prepare_pipeline_body()      # 可选图片预分析
→ runtime.pipeline._resolve_intent()
   ├─ message_rules / intent_resolution 确定性规则
   └─ stages.intent.run_intent() → LLM 兜底
→ runtime.pipeline._merge_followup_context()
→ runtime.pipeline._missing_slots()
→ stages.slot_checker.check_required_slots()
→ runtime.pipeline._dispatch_intent_handler()
→ INTENT_HANDLERS[resolved_intent]
```

推荐意图进入：

```text
handlers.handle_recommendation()
→ criteria_from_intent()              # 投机 Criteria
→ stages.criteria.run_criteria()      # 正式 Criteria
→ continue_recommendation_from_criteria()
```

### 3.4 关键数据结构

| 数据结构 | 作用 |
|---|---|
| `ChatStreamRequest` | HTTP 请求 DTO，包含 message、image_url、session_id、history 等 |
| `IntentResult` | 表示用户要执行什么动作，并携带初步约束 |
| `Constraints` | 封闭的购买约束字段集合 |
| `CriteriaPayload` | 检索与推荐共同使用的正式购买标准 |
| `PipelineStages` | 将阶段函数注入 Pipeline，便于替换和测试 |
| `StreamContext` | 保存 session、turn、seq、取消令牌、阶段函数和耗时 |

### 3.5 为什么 Intent 和 Criteria 必须分开

Intent 表示动作，例如：

```text
recommend
compare
add_to_cart
view_cart
feedback
continue
```

Criteria 表示如何筛选和解释商品，例如：

```text
category = 美妆护肤
product_type = 洗面奶
budget_max = 200
skin_type = 油性
ingredient_avoid = [酒精]
```

如果合并二者，会产生两个问题：

1. 路由动作和检索约束互相污染，例如“加购”不应该重新生成一套商品标准。
2. LLM 输出会直接进入检索层，字段不受控、历史合并和审计都变得困难。

封闭 DSL 的价值不是“所有字段都做 SQL 过滤”，而是：

- 字段集合受控。
- 类型和默认值受控。
- 可以做确定性合并、净化和审计。
- 检索、卡片和多轮状态共享同一种语义。

### 3.6 为什么不让 LLM 直接路由所有请求

确定性规则适合：

- 加购、查看购物车、换一组等明确命令。
- 预算、品牌排除等可以稳定提取的表达。
- 低成本、低延迟且必须保持一致的业务动作。

LLM 适合：

- 省略严重、口语化或语义模糊的表达。
- 需要结合历史和图片上下文的判断。
- 规则无法覆盖的长尾语言。

模型输出仍然不能直接使用，后续还会执行：

```text
Pydantic 校验
→ 品类和商品类型归一化
→ 约束确定性提取与修正
→ 历史上下文合并
→ 槽位检查
→ Handler 白名单路由
```

### 3.7 高频追问

**Q：这是真正的 ReAct Agent 吗？**

> 不是典型的开放式 ReAct 循环。主链路是确定性 Workflow：阶段、工具和事件顺序由代码控制，LLM 只在意图理解、标准生成、文案和解释等受限任务中参与。这样牺牲了一部分开放探索能力，但更适合比赛中的电商导购场景，因为预算、品类、加购和协议都要求可控。

**Q：为什么不用 LangChain？**

> 项目需要精确控制 Intent/Criteria 的状态演变、投机检索并发、SSE 事件顺序、取消和错误边界。直接使用 FastAPI、Pydantic 和 async generator 编排，运行路径更透明，也更容易把每个阶段单独测试。LangChain 并不是不能实现，而是对这个三周项目会增加抽象和调试成本。

**Q：阶段真的完全独立吗？**

> 不是业务上毫无依赖。Retrieval 必须消费 Criteria，Recommendation 必须消费商品和证据。这里的独立是指接口边界明确、通过结构化 DTO 交互，并且阶段函数可以在测试中替换，不是说执行顺序可以任意交换。

**Q：槽位检查为什么不直接放到 Criteria 之后？**

> 槽位检查位于 Intent 后、Handler 分发前，用于判断当前业务动作是否具备最低必要信息。Criteria 负责形成完整购买标准；Slot 负责决定当前是否可以继续执行。学习顺序可以先讲 Criteria，但真实运行顺序仍然是 Intent 后先检查必要槽位，再进入对应 Handler。

### 3.8 当前真实边界

- 规则覆盖率没有独立、稳定的统计，不能把“80%”当作正式指标。
- Criteria 的部分字段是偏好或解释信息，不是全部都参与硬过滤。
- 品类切换后的 `product_type` 强制覆盖可能没有同步更新 summary 和 field_sources。
- 项目是确定性 Workflow 加受控 LLM，不应包装成自由规划的 Multi-Agent 系统。

## 4. 卖点二：投机检索与异步并发

### 4.1 对应简历表达

> 基于意图中的品类、预算构造投机 Criteria 提前检索，使 pgvector 查询与正式 Criteria 生成并行；完整标准返回后执行内存二次过滤，不满足则回退串行检索。图片理解、视觉向量和反馈读取等 I/O 使用 `asyncio` 并发编排，缩短关键路径等待。

### 4.2 30 秒回答

> 常规链路要等 Criteria LLM 完成后才开始检索，但 Intent 阶段通常已经得到品类、预算和商品类型等核心约束。我先用这些字段构造临时 Criteria，后台启动检索，同时生成正式 Criteria。正式结果回来后，用完整约束对最多十几个投机候选做内存二次过滤；如果候选为空，再用正式 Criteria 串行检索。它本质上是在不改变最终约束语义的前提下，让模型推理与检索 I/O 时间重叠。

### 4.3 完整调用链

```text
handlers.handle_recommendation()
├─ asyncio.create_task(get_feedback_context())
├─ 可选：启动 image embedding
├─ criteria_from_intent(intent) → spec_criteria
├─ 等待必要的 feedback / image embedding
├─ start_stage_task(run_retrieval(spec_criteria, top_n=12))
└─ run_with_heartbeat(run_criteria(...))
      ↓ 两者并行
正式 Criteria 返回
→ await retrieval_task
→ _post_filter_retrieval(precomputed, formal_criteria, feedback)
→ 有候选：复用投机检索结果
→ 无候选：continue_recommendation_from_criteria() 重新正式检索
```

需要准确表述：投机检索与正式 Criteria 生成并行；图片 Embedding 会更早启动，但当前代码在启动投机检索前会等待图片 Embedding 结果，因此不能笼统说所有任务始终完全并行。

### 4.4 投机 Criteria 与正式 Criteria 的区别

| 方面 | 投机 Criteria | 正式 Criteria |
|---|---|---|
| 来源 | `IntentResult.extracted_constraints` | LLM、历史 Criteria、criteria_patch、反馈与后处理 |
| 生成成本 | 纯内存映射 | 可能包含外部模型调用 |
| 完整性 | 临时、不完整 | 当前轮正式标准 |
| 用途 | 提前召回候选 | 最终过滤、展示和推荐 |
| 失败处理 | 丢弃结果 | 使用正式 Criteria 重新检索 |

### 4.5 为什么二次过滤不能省略

Intent 可能只提取到：

```text
category = 美妆护肤
product_type = 防晒
budget_max = 200
```

正式 Criteria 还可能包含：

```text
ingredient_avoid = [酒精]
brand_avoid = [...]
skin_type = 敏感
```

如果直接使用投机结果，就可能让缺失的严格约束被绕过。二次过滤使用正式 Criteria 对投机候选进行确定性复核，作用类似乐观执行后的提交校验。

### 4.6 为什么失败时回退串行仍然有价值

投机优化不能改变正确性边界：

- 投机任务异常：记录 warning，`precomputed=None`。
- 正式 Criteria 改变了购物策略：丢弃投机结果。
- 二次过滤后为空：使用正式 Criteria 串行检索。

因此它是性能优化，不是正确性依赖。最坏情况只是重新走原始串行路径，而不是返回错误候选。

### 4.7 高频追问

**Q：为什么不用 `asyncio.gather()`？**

> 核心不是 API 形式，而是任务生命周期不同。投机检索需要作为后台任务提前启动，正式 Criteria 则通过 `run_with_heartbeat()` 持续向 SSE 产出 thinking 事件。使用显式 Task 可以独立记录耗时、检查完成状态、捕获异常并决定是否复用结果。

**Q：`top_n=12` 是怎么来的？**

> 它是比赛规模下的经验参数，用于给正式 Criteria 的二次过滤预留候选余量，不是经过严格参数搜索得到的通用最优值。生产化应记录投机命中率、后过滤淘汰率和重检率，再通过评测选择候选规模。

**Q：二次过滤是不是没有额外 I/O？**

> `_post_filter_retrieval()` 本身是内存过滤，没有外部 I/O；但如果过滤后为空，后续正式重检仍会发生 Embedding、数据库召回和 Rerank I/O。因此只能说“投机命中时二次过滤是轻量内存操作”，不能说整个机制永远没有额外 I/O。

**Q：异步等于多线程吗？**

> 不等于。这里主要是单事件循环上的协作式并发，适合等待数据库和模型 HTTP 请求。任务在 `await` 时让出执行权；CPU 密集型计算不会因为 `asyncio` 自动获得并行加速。

### 4.8 当前真实边界

- 没有当前版本可复现的 P50/P95 对照数据，因此简历应强调“重叠关键路径”，不要写固定降幅。
- 投机检索依赖当前检索链路；`VectorSearchFilters` 参数契约问题可能使真实 SQL 召回提前失败。
- 图片 Embedding 在投机检索启动前被等待，图片场景的并发仍有进一步优化空间。
- 检索缓存 Key 未包含 `top_n`，投机 `top_n=12` 与普通检索可能错误复用结果。

## 5. 卖点三：数据加工与混合检索

### 5.1 对应简历表达

> 将 100 件商品按营销描述、FAQ、评价和风险加工为 1292 个 1024 维 Chunk；构建 pgvector 语义召回、Python 硬约束复核、BM25/RRF 关键词排序增强、Rerank 精排与商品聚合链路；支持文本和图片向量检索，无结果时渐进放宽预算，品类不退让。

### 5.2 30 秒回答

> 商品不是整件生成一个向量，而是按 profile、营销描述、每条 FAQ、每条评价、风险摘要和比较维度拆成带角色的语义 Chunk。在线查询先把 Criteria 转成检索文本并生成 Embedding，通过 pgvector 找语义相关 Chunk，再用 Python 复核预算、品类和排除项。BM25 和 RRF 为品牌、型号等精确词增加排名信号，Rerank 对小候选集精排，最后按 `product_id` 聚合成商品并绑定命中 Chunk 作为证据。

### 5.3 离线数据链路

```text
data/raw/ecommerce_agent_dataset/*.json
→ repos.products.list_raw_products()
→ services.product_ingest.seed_products()
→ chunking.build_product_knowledge_package()
→ chunking.build_product_chunks()
→ embedding.embed_texts(batch_size=10)
→ products / product_chunks
→ pgvector HNSW 索引
→ BM25Index 从数据库 Chunk 构建内存索引
```

Chunk 类型包括：

| Chunk 类型 | 来源 | 作用 |
|---|---|---|
| `profile` | 名称、品牌、品类、价格、别名等 | 商品身份和基础属性召回 |
| `marketing` | 营销描述 | 推荐理由 |
| `faq` | 每条官方问答 | FAQ 或风险证据 |
| `positive_review` | 非低分评价 | 用户体验证据 |
| `negative_review` | 低分评价 | 风险证据 |
| `warning` | 规则生成的风险摘要 | 风险补充 |
| `compare` | 品类比较维度 | 商品对比 |

### 5.4 在线检索调用链

```text
stages.recommendation.run_retrieval()
→ retriever.retrieve_with_evidence()
→ 检查进程内 RetrievalCache
→ criteria_query_text(criteria)
→ embedding.embed_text()
→ _sql_filters_for_recall()
→ _vector_recall_from_db()
→ repos.documents.list_vector_chunks_by_similarity()
→ 可选：图片向量召回任务
→ 无结果时 _relaxation_attempts()
→ BM25Index.search()
→ rrf_merge()
→ Python _passes_hard_filters()
→ _rerank_chunk_hits()
→ 按 product_id 聚合、去重
→ _evidence_by_product()
→ RetrievalOutput(products, evidence_by_product, trace_details)
```

### 5.5 各组件分别解决什么问题

| 组件 | 输入与输出 | 解决的问题 |
|---|---|---|
| Chunking | 商品知识 → 多段语义文本 | 避免整件商品文本语义混杂 |
| Embedding | 文本/图片 → 1024 维向量 | 将语义转换为可计算坐标 |
| pgvector | 查询向量 → 相似 Chunk | 大范围语义粗召回 |
| Python 硬过滤 | 商品 + Criteria → 通过/拒绝 | 复核预算、品类、排除项 |
| BM25 | 查询文本 → 关键词排名 | 品牌、型号、专有词匹配 |
| RRF | 多个排名 → 融合排名 | 避免不同原始分数量纲冲突 |
| Rerank | query-document 对 → 相关性分 | 对有限候选进行更精确匹配 |
| 商品聚合 | Chunk hits → ProductPayload | 对客户端返回完整商品而非碎片 |
| Evidence 绑定 | 商品 → 命中 Chunk | 解释推荐依据 |

### 5.6 Chunk 为什么比整件商品更适合召回

一件商品可能同时包含：

- “控油效果好”的正面评价。
- “敏感肌可能刺激”的风险评价。
- 与推荐问题无关的物流或规格信息。

如果全部拼成一个向量，这些语义会被压缩到同一个坐标中，检索只能知道“整件商品大致相关”，难以说明是哪句话命中。Chunk 级召回能够：

- 提高局部语义匹配精度。
- 区分推荐理由、FAQ 和风险。
- 直接把命中原文绑定为 Evidence。

但 Top-K Chunk 召回不保证找全一件商品的全部评价。因此当前设计把“候选召回”和“风险证据补查”分开：先用正向 Chunk 找候选，再按商品 ID 补充风险证据。

### 5.7 SQL 预过滤与 Python 硬过滤

设计目标是：

```text
SQL 预过滤
→ 在向量查询前缩小搜索空间

Python 硬过滤
→ 对召回后的商品执行完整业务复核
```

SQL 适合数据库字段可以直接表达的条件；Python 层适合别名、领域词和复杂规则。二者不是重复浪费，而是“数据库提前裁剪 + 业务层最终校验”。

但当前提交版本存在真实缺陷：`retriever._sql_filters_for_recall()` 构造 `VectorSearchFilters` 时传入了 DTO 中不存在的参数名，并遗漏了预算下推。面试时必须区分：

- 设计目标：SQL 先缩小候选，再做向量召回。
- 当前行为：SQL Filter DTO 契约漂移，可能在查询前抛 `TypeError`。
- 修复方案：统一使用 `budget_max`、`product_type_aliases`、`brand_avoid`、`avoid_product_ids`，并增加真实 Repo 集成测试。

### 5.8 BM25 当前是否是真正独立召回

BM25 会搜索全量 Chunk，并与向量排名进入 RRF。但 RRF 后通过 `chunk_by_id` 还原对象时，字典只包含原向量命中：

```text
BM25-only chunk
→ 出现在 merged_ids
→ 不在 chunk_by_id
→ 被跳过
```

因此准确表述是：

> 当前 BM25 为向量候选提供关键词排名增强，还没有完整扩大候选并集。

改进方式是根据 BM25-only 的 chunk ID 补查数据库，构造对应 `ProductHit` 后再进入统一过滤和 Rerank。

### 5.9 Rerank 与向量召回有什么区别

Embedding 采用双塔思路：

```text
query → query vector
document → document vector
→ 计算距离
```

优点是文档向量可以预计算，适合大范围召回；缺点是 query 和 document 编码时没有直接交互。

Rerank 同时读取 query 和 document，对少量候选重新判断相关性。它更精确，但计算成本更高，因此放在召回之后，不能代替向量数据库扫描全库。

### 5.10 渐进式放宽

严格召回为空时，预算按配置依次放宽：

```text
原预算
→ ×1.3
→ ×1.5
→ 移除上限
```

品类和 `product_type` 不参与放宽，因为“预算稍超”和“商品种类错误”的业务后果不同。

需要承认的边界：

- 最后移除预算上限可能偏离用户预期。
- 放宽必须在前端明确提示。
- 当前 Trace 写入位置与 Handler 读取位置不一致，预算放宽提示可能失效。

### 5.11 高频追问

**Q：为什么不用 Elasticsearch？**

> 当前只有 100 件商品和 1292 个 Chunk，PostgreSQL 同时承担结构化数据、会话状态和 pgvector 检索，部署成本最低。BM25 用进程内索引补充关键词信号。数据扩大、需要复杂倒排检索、分片和独立扩缩容时，再考虑 Elasticsearch/OpenSearch。

**Q：HNSW 参数怎么调的？**

> 当前没有做系统参数搜索，建索引时主要使用 pgvector 默认配置。当前规模不足以证明参数最优；扩展时应以 Recall@K、查询延迟、索引构建成本和内存占用联合评估 `m`、`ef_construction` 和查询 `ef_search`。

**Q：为什么先检索 Chunk，最后却返回商品？**

> Chunk 是检索和证据单位，商品是业务展示和决策单位。多个 Chunk 可以命中同一商品，系统按 `product_id` 聚合、去重，并保留相关 Chunk 作为 Evidence。

**Q：图片和文本向量是不是同一个模型、同一个索引？**

> 不是。文本使用 `text-embedding-v3`，商品 Chunk 写入 `product_chunks`；图片使用 `qwen3-vl-embedding`，写入商品图片向量表。在线检索分别执行文本和图片相似度查询，再在商品层合并。

### 5.12 当前真实边界

- `VectorSearchFilters` 参数契约不一致，是当前最严重的检索入口问题。
- BM25-only Chunk 会丢失，不能宣称完整 Sparse + Dense 并集召回。
- 图文合并是文本优先追加，不是统一分数融合。
- Rerank 没有正式降级路径，Provider 失败可能中断推荐。
- 检索缓存是进程内状态，Key 不含 `top_n`，也没有数据版本失效。
- 当前数据规模不能证明十万或百万商品下的性能。

## 6. 卖点四：证据、防幻觉与确定性决策

### 6.1 对应简历表达

> 推荐理由绑定命中 Chunk 原文，以候选校验、23 项禁止词和价格扫描拦截不可验证内容；按检索相关性、标准匹配、用户反馈、证据和风险确定性评分锁定最终商品，LLM 只负责解释，降低幻觉与决策漂移。

### 6.2 30 秒回答

> 防幻觉不是只靠 Prompt。商品事实和证据来自数据库，推荐模型只能看到候选商品和对应 Chunk；输出后还会校验是否引用了候选集外商品，并拦截库存、包邮、优惠券等 23 类不可验证商业声明。价格声明在流式正文完成后与商品、SKU 和预算白名单比对，异常时追加纠偏提示。最终选哪个商品也不交给 LLM，而是由五因子确定性评分锁定，LLM 只解释结果。

### 6.3 防幻觉的分层

```text
数据层
→ ProductPayload 来自数据库，商品和价格不是 LLM 创建

检索层
→ EvidencePayload 绑定命中 Chunk 原文

生成输入层
→ LLM 只接收候选商品与证据上下文

生成输出层
→ 校验候选商品名、商品 ID 和 23 项禁止商业声明

流式后置层
→ validate_price_claims() 检查价格数字并追加纠偏

决策层
→ 确定性评分选择赢家，LLM 仅解释
```

### 6.4 证据如何与商品绑定

检索先得到 Chunk hits，每个 hit 含 `product_id`。聚合商品后：

```text
product_id
→ 收集命中 Chunk
→ 转为 EvidencePayload(source_id, snippet, score...)
→ evidence_by_product[product_id]
→ ProductCardEvent.evidence
→ 写入 evidence_links 表
```

风险 Chunk 通常不参加正向主召回，候选商品确定后再按商品 ID 补充风险说明。这避免负面评价因为文本高度相关而把商品顶到推荐前列。

### 6.5 23 项禁止词如何工作

`_FORBIDDEN_COMMERCIAL_TERMS` 包含库存、现货、优惠、包邮、运费、次日达、购买链接、物流等不可由当前数据库验证的声明。

推荐正文的非流式校验逻辑是：

```text
RecommendationResult.text_chunks
→ _validate_recommendation_chunks()
→ 空正文检查
→ 候选集外商品检查
→ 禁止词检查
→ 命中则抛出 RuntimeError
```

最终决策文案采用更温和的 `_sanitize_decision()`，会将禁止词替换为安全表述。两条路径的处理方式并不完全相同，面试时不要统一说成“全部命中后拒绝”。

### 6.6 价格 Grounding 的真实时机

多商品推荐正文通过 `text_delta` 发送完成后：

```text
captured_turn_text_parts
→ validate_price_claims(text, products, budget)
→ 若存在不允许的价格数字
→ 再发送一段纠偏 text_delta
```

因此它不能撤回已经发出的错误数字，只能追加纠偏。更严格的生产化方案包括：

- 将价格从 LLM 自由文本中移除，由模板渲染。
- 在发送前做小缓冲和校验。
- 使用结构化声明对象而不是扫描自然语言。

### 6.7 最终决策评分

确定性评分公式：

```text
final_score =
retrieval_score × 0.35
+ criteria_match × 0.25
+ user_signal × 0.25
+ evidence_score × 0.10
- risk_penalty × 0.05
```

五类信号分别表示：

| 信号 | 含义 |
|---|---|
| retrieval | 检索阶段相关性或候选位置 |
| criteria_match | 预算、肤质、场景等标准匹配 |
| user_signal | 喜欢、查看详情、加购、不感兴趣等反馈 |
| evidence | 证据数量和 snippet 丰富度 |
| risk | 明确排除、反感或约束冲突 |

调用链：

```text
continue_decision_from_current_deck()
→ get_feedback_context()
→ score_candidates()
→ decision_confidence()
→ 锁定 winner_product_id
→ stages.decision.run_decision(..., locked_winner)
→ LLM 生成 why / not_for 等解释
→ FinalDecisionEvent
```

这样做的核心原因是：

> 排名和业务约束是可审计决策，语言模型适合解释，不适合作为不可控的最终裁判。

### 6.8 高频追问

**Q：RAG 为什么仍然会幻觉？**

> RAG 只给模型提供上下文，不能保证模型严格只使用上下文。模型仍可能补全常见电商话术、引用候选外商品或改写价格。因此必须结合结构化事实、候选白名单、证据绑定和输出校验。

**Q：Evidence 是不是能证明推荐正文的每一句都来自原文？**

> 不能。它能证明推荐商品有对应检索证据，Prompt 也把证据提供给模型，但当前没有对生成文案逐句做 entailment 校验。更准确的说法是“提供可追溯依据并降低幻觉”，不是“数学上保证每句话真实”。

**Q：为什么不让 LLM 综合所有信息选赢家？**

> LLM 的选择可能受提示顺序、措辞和随机性影响，也很难解释具体权重。确定性评分可复现、可审计，可以明确说明用户反馈和风险如何影响结果；LLM 保留在它擅长的自然语言解释环节。

**Q：固定权重是不是拍脑袋？**

> 当前权重是比赛阶段的业务启发式，不是经过线上学习得到的最优参数。生产化应保存曝光、点击、反馈和转化数据，通过离线回放、A/B 测试或 Learning-to-Rank 调整；涉及风险和硬约束的部分仍不应完全交给学习模型。

### 6.9 当前真实边界

- Evidence 不是逐句事实验证。
- 价格校验发生在流式发送后，只能追加纠偏。
- 禁止词是硬编码的全局词表，缺少按品类配置和版本管理。
- `EvidencePayload` 对证据类型的传递能力有限。
- 决策评分权重是启发式，当前数据规模不足以验证泛化效果。
- `_compute_risk_penalty()` 等逻辑还可以覆盖更多硬约束冲突。

## 7. 卖点五：SSE 流式协议与可靠性

### 7.1 对应简历表达

> SSE 推送 10 种结构化事件，耗时阶段每 0.8 秒检查取消并发送 thinking 心跳；已输出后失败不重试。通过 `turn_id/seq` 隔离轮次并保证顺序，加载时校验事件类型与 JSON Schema，不一致则阻止启动。

### 7.2 30 秒回答

> 导购链路主要是服务端持续向客户端推送状态和结果，因此选择 SSE 而不是 WebSocket。后端不是只推字符串，而是定义 thinking、criteria_card、product_card、text_delta、final_decision、done、error 等 10 种事件。每个事件带 session、turn、seq 和 event_id；耗时阶段使用 `asyncio.wait(timeout=0.8)` 周期性检查取消并发 thinking。响应头提交后发生错误不能再改 HTTP 状态，只能发送 SSE error 和 done。

### 7.3 HTTP 与 SSE 两层边界

```text
api.chat.stream_chat()
→ 处理 HTTP 请求校验、响应头和 SSE 序列化

runtime.pipeline.chat_stream()
→ 管理一轮会话生命周期、取消、异常、done 和清理
```

建立流之前：

- 请求 DTO 校验失败可以返回 HTTP 4xx。
- 依赖或权限错误可以返回正常 HTTP 错误。

流建立之后：

- HTTP 200 和响应头已经提交。
- 业务异常必须转成 `error` 事件。
- 随后发送 `done(finish_reason=error)` 结束本轮。

### 7.4 SSE 事件信封

公共字段包括：

```text
schema_version
event
session_id
turn_id
seq
event_id
timestamp_ms
node_id（部分事件）
```

字段职责：

| 字段 | 作用 |
|---|---|
| `session_id` | 标识完整会话 |
| `turn_id` | 隔离同一会话中的一次发送 |
| `seq` | 保证单 turn 内事件顺序 |
| `event_id` | 客户端去重 |
| `node_id` | 更新同一个逻辑 UI 节点 |
| `deck_id` | 关联同一批候选商品和反馈 |
| `message_id` | 聚合连续文本增量 |

### 7.5 心跳并不是 LLM 超时

核心逻辑：

```python
done, _ = await asyncio.wait(
    {task},
    timeout=ctx.heartbeat_interval_seconds,
)
```

含义是：

- 任务在 0.3 秒完成：立即返回，不等待满 0.8 秒。
- 0.8 秒仍未完成：检查取消状态，发送 thinking，再继续等。
- 任务可以运行多个心跳周期。

所以 0.8 秒是单次等待和取消检查周期，不是模型总超时。心跳由各耗时阶段分别调用，不是从请求开始到结束的唯一全局定时器。

### 7.6 取消机制

```text
POST /cancel
→ 本进程 CancellationToken 快速标记
→ 数据库记录 cancel request

Pipeline / run_with_heartbeat()
→ ensure_active()
→ 检查进程内 token
→ 检查数据库取消状态
→ 抛出 StreamCancelled
→ chat_stream() 发送 done(cancelled)
→ finally 清理 turn 注册
```

它是协作式取消：任务在检查点观察取消状态后退出，不是强制杀死系统线程。

### 7.7 为什么流式输出后不自动重试

假设客户端已经收到：

```text
“推荐理由第一段……”
```

如果 Provider 失败后从头重试，客户端可能继续收到：

```text
“推荐理由第一段……”
```

这会造成重复正文、message_id 状态混乱和不可预测的 UI。项目的策略是：

- 未发送正文前可以切换 Provider。
- 已经产生流式增量后，失败则结束当前流并暴露错误。
- 用户可以重新发起一轮，而不是服务端悄悄重放半轮。

### 7.8 协议守卫的真实范围

模块加载时 `_verify_protocol_consistency()` 比较：

```text
contracts/sse-events.schema.json 中的事件类型集合
vs
Python EVENT_TAG_MAP
```

不一致时抛 `ImportError`，阻止服务启动。

需要准确表述：

- 它校验的是事件类型集合，不是完整 JSON Schema 的每个字段。
- Android 契约通过独立 Kotlin/静态测试和 CI 检查。
- 因此不能只说“启动时自动完整校验前后端所有协议字段”。

### 7.9 高频追问

**Q：为什么用 SSE，不用 WebSocket？**

> 当前主要数据方向是请求建立后由服务端连续推送结构化事件，客户端的后续动作通过新的 HTTP 请求发送。SSE 与 HTTP 基础设施兼容、服务端实现简单，也适合 Android OkHttp。若未来需要高频双向协作、实时多人状态或长连接命令通道，再考虑 WebSocket。

**Q：SSE 自动重连会不会重复执行请求？**

> Android 端不应该把连接重连等同于安全重放业务请求。项目依靠 turn_id、event_id 和客户端状态做隔离与去重，但当前没有实现完整的服务端事件回放游标。生产化需要幂等键、Last-Event-ID 和事件存储配合。

**Q：如果发送三张商品卡后推荐文案失败，商品卡保留吗？**

> 已发送事件无法撤回。后端发送 error/done 结束本轮，客户端可以保留已经收到的真实商品卡，并将本轮标记为失败或不完整。不能再返回 HTTP 500。

### 7.10 当前真实边界

- 心跳不是严格网络层 keepalive，也不是客户端离线判定协议。
- import-time guard 只比较事件类型，不做完整字段级校验。
- 取消是协作式、best-effort；外部 Provider 请求是否立即停止取决于任务取消传播。
- 当前没有完整 Last-Event-ID 服务端回放机制。
- 流式价格校验发生较晚，已发送内容无法撤回。

## 8. 卖点六：多轮状态、反馈、可观测性与评测

### 8.1 对应简历表达

> 多轮会话持久化 Criteria、候选集和反馈，品类切换时清理相关约束，反馈注入后续检索与决策；贯通 LLM、SSE、检索 Trace、证据和审计，以完整 `chat_stream` 驱动确定性指标与 LLM Judge 双轨评测。

### 8.2 30 秒回答

> 多轮状态分为“用户说过什么”和“用户做过什么”。历史 Criteria、候选商品和 deck 保存在会话快照中；like、dislike、查看详情和加购等行为保存在 feedback 表。下一轮会按本轮优先原则合并 Criteria，品类切换时清理品牌和商品类型等品类相关字段，反馈则进入检索过滤和最终决策评分。为了排查 Agent 链路，系统按 turn 关联请求日志、LLM 调用、SSE 事件、检索 Trace、证据链接和审计事件；评测直接运行完整 `chat_stream()`，而不是只测单个 Prompt。

### 8.3 两类状态

| 状态 | 保存内容 | 主要用途 |
|---|---|---|
| Conversation 快照 | Criteria、候选 product_ids、deck_id、对话摘要 | 多轮约束继承、continue、对比和决策 |
| Feedback 事件 | like、dislike、view_detail、open_evidence、add_to_cart 等 | 排除商品、排序信号和决策收敛 |

约束继承回答“用户说过什么”，反馈闭环回答“用户做过什么”。

### 8.4 多轮合并与话题切换

```text
当前 Intent
→ get_previous_criteria(session_id)
→ _should_merge_previous_context()
→ _is_topic_switch()
→ 本轮明确字段优先
→ 缺失字段从历史补充
```

基本原则：

- 本轮用户明确修改的字段覆盖历史。
- 本轮没有提到的字段才可能继承。
- 品类或产品类型变化时，清理品牌和商品类型等强品类相关约束。
- 预算等通用字段可以保留，但仍需要根据实际语境谨慎处理。

### 8.5 Feedback 如何进入检索与决策

```text
Android 交互
→ POST /feedback
→ api.feedback
→ services.feedback.record_feedback()
→ repos.feedbacks
→ feedbacks 表

下一轮推荐
→ get_feedback_context(session_id)
→ avoid_products / avoid_traits 等
→ RetrievalFilters
→ Python 硬过滤

最终收敛
→ liked / disliked / viewed / add_to_cart 信号
→ score_candidates()
```

“换一组”和“不喜欢”不同：

- 不喜欢：记录对具体商品或特质的负反馈。
- 换一组：读取上一批 product IDs，临时加入排除集合，避免原样返回。

### 8.6 可观测性链路

```text
request_id / trace_id / session_id / turn_id
├─ api_request_logs
├─ audit_events
├─ observability_llm_calls
├─ observability_sse_events
├─ retrieval_traces
└─ evidence_links
```

按 turn 查询 Debug Bundle 时，可以回答：

- 这一轮收到了什么请求？
- 调了哪个模型和 Profile？
- 模型耗时、状态、fallback_from 是什么？
- 发出了哪些 SSE 事件，seq 是否连续？
- 检索应用了哪些条件、选中了哪些商品？
- 推荐证据来自哪些 Chunk？
- 是否发生 Criteria 丢失等上下文诊断事件？

LLM 和 SSE 观测写入采用 fire-and-forget 后台任务，失败只记录 warning，不阻塞主聊天链路。应用关闭时会等待这些任务一段时间。

### 8.7 评测体系

评测不是只调用 LLM，也不是只测试某个纯函数：

```text
run_eval()
→ 读取评测样本
→ _run_pipeline()
→ run_intent()
→ chat_stream()
→ 收集 criteria_card / product_card / text_delta / final_decision
→ 计算确定性指标
→ 调用 LLM Judge
→ 计算 overall_score
→ 持久化 EvalRun
```

当前输出口径：

**8 个确定性子指标**

1. intent_accuracy
2. constraint_extraction_accuracy
3. criteria_coverage
4. recall_at_5
5. recall_at_10
6. evidence_coverage
7. faithfulness
8. constraint_satisfaction

**6 个 LLM Judge 子指标**

1. context_precision
2. context_recall
3. answer_correctness
4. llm_constraint_satisfaction
5. multi_turn_consistency
6. ranking_reasonableness

再加 `overall_score`，合计 15 项输出指标。

78.4% 的正确表述：

> 这是 20 条固定样本、当前模型配置和当前代码版本下的离线验收综合分，不代表线上用户准确率，也不能证明所有场景达到 78.4%。

### 8.8 高频追问

**Q：为什么既要确定性指标，又要 LLM Judge？**

> Intent、商品 ID、预算和 Recall 等结构化结果可以精确计算，使用 LLM Judge 反而不稳定；回答正确性、上下文相关性和排序合理性更难写成完整规则，适合由模型辅助评估。双轨能够减少“所有指标都由另一个 LLM 主观打分”的问题。

**Q：LLM Judge 会不会自己不可靠？**

> 会。因此需要固定 Prompt、模型和样本，保留输入输出，并结合确定性指标。生产化还应进行人工抽样标注、评审一致性检查和多 Judge 对照，不能把单一 Judge 分数当成绝对真相。

**Q：可观测性会不会泄露用户隐私？**

> 当前支持保存 Prompt/Response 预览甚至完整 Payload，比赛调试方便，但生产环境必须默认脱敏、限制管理员权限、设置保留周期，并避免在 URL Query 中传敏感管理 Token。

**Q：多 Worker 下这些状态安全吗？**

> 会话和反馈保存在 PostgreSQL，可以跨 Worker；但检索缓存、BM25 索引和本进程取消 Token 是进程内状态。取消还有数据库路径补充，但缓存和 BM25 并不共享。生产化需要 Redis、独立检索服务或统一索引更新机制。

### 8.9 当前真实边界

- 20 条样本规模较小，不能证明统计显著性。
- Runner 输出是 8 个确定性 + 6 个 LLM Judge + overall，不是“8+8”。
- `STRICT_RUNTIME` 当前只被配置读取和 health 展示，没有统一控制业务 fallback。
- 默认测试会跳过部分集成和预发布用例，不能只看 passed 数量判断生产就绪。
- 可观测 Payload 需要脱敏、访问控制和生命周期管理。
- 数据库迁移依赖 `create_all + ADD COLUMN`，缺少 Alembic 版本历史和回滚。
- `/health` 更接近 liveness，不代表数据库、索引和 Provider 已 ready。

## 9. 模型与外部服务追问

### 9.1 LLM、Embedding 和 Rerank 的区别

| 类型 | 输入 | 输出 | 在项目中的作用 |
|---|---|---|---|
| LLM | 对话、Prompt、结构化上下文 | 文本或 JSON | Intent、Criteria、推荐解释、决策解释、对比与策略叙事 |
| VLM | 图片 + 文本 | 图片属性 JSON | 图片理解 |
| Text Embedding | 文本 | 1024 维向量 | 查询与 Chunk 语义召回 |
| VL Embedding | 图片 | 1024 维向量 | 图片相似商品召回 |
| Rerank | query + 多个 document | 每个候选的相关性分数 | 对粗召回候选精排 |

### 9.2 当前模型映射

以 [`llm_profiles.yaml`](../../backend/src/config/llm_profiles.yaml) 为准：

- Intent、Criteria、Recommendation、Decision、Comparison 和 Strategy Narration：Qwen-Turbo 主模型，Doubao 作为 Provider fallback。
- 图片理解：Qwen-VL-Plus，无 fallback。
- 文本 Embedding：text-embedding-v3，1024 维，无 fallback。
- Rerank：qwen3-rerank，无 fallback。
- 图片 Embedding：qwen3-vl-embedding，1024 维，无 fallback。

不要沿用旧文档中“Doubao 做 Intent Primary”“Qwen-Plus 做生成 Primary”或“Embedding 有 16 维确定性 fallback”的历史口径。

### 9.3 为什么通过任务接口，而不是 Runtime 直接调 SDK

Runtime 调用：

```text
analyze_intent()
generate_criteria()
stream_recommendation()
generate_decision()
analyze_image()
```

这些 task-oriented interface 将业务语义与 Provider 细节分离。Provider、模型、Base URL、超时和 fallback 放在 Profile 配置和 Gateway 中，避免 Pipeline 充斥 HTTP 传输代码。

### 9.4 重试与 Fallback 如何区分

- 重试：同一个 Profile 对瞬态传输故障再次调用。
- Fallback：Primary Profile 不可用时切换到另一个 Provider/Profile。
- 流式正文已经输出后：不能安全切换后从头重放。
- Embedding、Rerank、图片模型当前没有备用 Profile：失败应显式暴露。

### 9.5 为什么直接使用 HTTP Client

项目通过共享异步 HTTP Client 调用 OpenAI-compatible 对话端点及百炼专用 Embedding/Rerank 端点。优势是：

- 统一控制超时、错误分类和重试。
- 动态切换不同 Provider 的 Base URL 与 Key。
- 记录完整模型可观测信息。
- 避免不同 SDK 的行为差异。

代价是需要自己维护流式解析、错误码兼容和 Provider 契约。

## 10. 必须主动承认的源码缺陷

面试官问到缺陷时，使用四句话：

1. **设计目标**：原本希望解决什么。
2. **当前行为**：源码实际做到哪里。
3. **影响范围**：会导致什么问题。
4. **改进方案**：如何修复和验证。

### 10.1 高优先级缺陷表

| 问题 | 当前影响 | 面试表述 | 修复方向 |
|---|---|---|---|
| `VectorSearchFilters` 参数名不一致 | 文本或图片召回可能在 SQL 前抛 `TypeError` | SQL 预过滤是设计目标，提交版本存在 DTO 契约漂移 | 对齐字段并增加 Repo 集成测试 |
| `_sql_filter_payload()` 读取旧字段名 | Trace 序列化也可能异常 | 过滤 DTO 重构未同步所有消费者 | 以 DTO 定义为唯一契约 |
| BM25-only Chunk 被丢弃 | 不是完整双路候选并集 | BM25 当前主要增强向量候选排序 | 补查 BM25-only Chunk 并构造 Hit |
| 图文结果文本优先追加 | 没有统一分数融合 | 当前支持双通道候选，不是成熟多模态融合排序 | 分数校准、加权融合或学习排序 |
| 视觉证据补充调用存在 async/参数问题 | 视觉增强路径可能降级或报错 | 主文本链路可解释，视觉补证仍需修复 | 修正 await、类型和字段契约 |
| Rerank 无正式 fallback | Provider 失败可能终止推荐 | 当前把 Rerank 视为关键外部依赖 | 增加确定性粗排降级并记录事件 |
| 缓存 Key 不含 `top_n` | 不同候选数量可能错误复用 | 缓存是进程内优化，不是强一致组件 | Key 加 top_n、数据和模型版本 |
| 放宽 Trace 写读位置不一致 | 预算放宽提示可能丢失 | 检索执行了放宽，但上层提示读取契约漂移 | 统一 Trace Schema |
| 价格校验在流式正文之后 | 已发错误无法撤回 | 当前采用追加纠偏 | 结构化价格或发送前缓冲校验 |
| `STRICT_RUNTIME` 未统一接线 | 开关不能控制全部降级行为 | 目前只是配置和展示字段 | 各 Service 统一消费运行策略 |
| `/health` 只有浅层检查 | 不能证明 RAG 就绪 | 当前是 liveness | 增加 DB、索引、Provider readiness |
| 无 Alembic | 缺少迁移历史和回滚 | 当前适合 Demo 初始化，不是成熟生产迁移 | 引入 Alembic，迁移与启动分离 |

### 10.2 一个完整缺陷回答示例

**Q：你说 SQL 预过滤，但代码是否真的能跑？**

> 设计目标是在 pgvector 相似度查询前，通过品类、预算、商品类型和排除项缩小搜索空间。当前提交版本里，`_sql_filters_for_recall()` 和 `VectorSearchFilters` 的字段名发生了契约漂移，例如调用方仍传旧的 `product_type`、`avoid_brands`，因此真实路径可能在 SQL 前抛参数错误。这会影响正常文本和图片召回，但不否定 SQL 预过滤的架构目标。修复时我会以 DTO 定义为单一真相源，对齐 `budget_max/product_type_aliases/brand_avoid/avoid_product_ids`，并用真实 PostgreSQL Repo 集成测试覆盖构造和查询。

这种回答比掩饰缺陷更能体现源码理解。

## 11. 综合架构追问

### 11.1 这个项目最核心的技术决策是什么

> 最核心的不是用了 pgvector，而是把不确定的模型能力限制在确定性业务边界内：Intent 和 Criteria 使用封闭模型，检索必须经过硬约束复核，商品事实来自数据库，最终赢家由确定性评分选择，SSE 协议由 Schema 约束。LLM 主要承担自然语言理解和解释。

### 11.2 如果扩大到十万商品，首先改什么

1. 修复并验证 SQL 预过滤，评估过滤选择性。
2. 对 HNSW 参数、Recall@K 和延迟做基准测试。
3. 将 BM25 从进程内索引迁移到独立检索服务或 OpenSearch。
4. 让文本和稀疏召回形成真正候选并集。
5. 控制 Rerank 候选规模并增加降级。
6. 缓存加入版本、分布式共享和失效策略。
7. 将离线 Embedding、重建索引和评测迁移到任务队列。
8. 增加 readiness、迁移系统、限流和容量指标。

### 11.3 为什么没有使用 Celery 和 Redis

> 比赛主链路以请求内短任务和 SSE 为主，`asyncio` 足以并发等待模型、数据库和图片服务。当前数据只有 100 件商品，引入 Celery 和 Redis 会增加部署与一致性成本。生产化后，离线向量重建、批量评测、图片处理适合进入任务队列；跨 Worker 缓存、限流和分布式锁再使用 Redis。

### 11.4 为什么没有做真正 Multi-Agent

> 导购任务的业务状态、约束和客户端协议都比较明确，使用多个自由 Agent 会增加 Token 成本、延迟、循环和不可预测性。当前采用单 Pipeline 加任务化模型接口，在需要策略、比较或购物车时走确定性分支。若未来出现独立工具域和长任务，可以评估 Planner-Executor，但不应为了名字引入多 Agent。

### 11.5 怎么证明项目不是简单套壳

可以从四层回答：

1. **业务控制层**：Intent、Slot、Criteria、Handler 和多轮状态。
2. **RAG 层**：语义 Chunk、Embedding、pgvector、BM25/RRF、Rerank、Evidence。
3. **可靠性层**：SSE 事件协议、取消、错误边界、候选校验和确定性决策。
4. **工程闭环**：PostgreSQL 持久化、Docker、可观测性、评测和测试门禁。

## 12. 行为面试素材

### 12.1 最难定位的问题

推荐选择“Embedding Batch Size 与静默降级”作为素材，但回答时必须使用当前正确口径：

> 早期批量 Embedding 的 Batch Size 超过 Provider 限制，调用失败后测试 fallback 让系统表面仍可运行，但索引维度和真实模型不一致。问题的难点不是 400 错误本身，而是降级掩盖了根因。后来通过严格 live smoke、维度校验和降级可观测性定位，并将批次调整为 10。这个问题让我意识到 fallback 不能只保证不崩，还必须记录是否降级、为什么降级以及结果语义是否变化。

不要再说“当前 `STRICT_RUNTIME=1` 会统一禁止 fallback”，因为当前源码中该开关没有完整接线。

### 12.2 一个性能设计取舍

> Criteria 生成和检索原本是串行依赖，但 Intent 已经包含部分可用约束。我把它转换成临时 Criteria 提前检索，正式 Criteria 返回后再二次校验。这样没有牺牲约束正确性，投机失败仍可回到串行路径。当前缺少稳定 P95 数据，所以我把它表述为关键路径并发设计，而不是宣称固定提升百分比。

### 12.3 一个架构取舍

> 最终决策没有直接交给 LLM，而是用检索、标准匹配、行为信号、证据和风险五类信号确定性评分。这样结果可复现、可解释，LLM 只负责把评分结果转换成自然语言。代价是权重需要人工设计，后续应通过真实反馈和 A/B 测试校准。

### 12.4 如果重新设计

优先回答三个方向：

1. 修复检索 DTO 契约并建立真实 PostgreSQL 集成测试。
2. 实现真正的 Dense + Sparse 候选并集和图文分数融合。
3. 建立生产级迁移、readiness、分布式缓存与敏感数据治理。

不要把“再加更多 Agent”作为第一答案。当前项目最需要的是契约正确性和生产化，而不是更复杂的概念包装。
