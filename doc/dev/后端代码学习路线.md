# BuyPilot-AI 后端代码学习路线

## 学习原则

1. **自顶向下，先看全景再钻细节** — 先追一次完整的请求生命周期（用户输入 → SSE 事件流），脑子里有了"高速公路"之后再下匝道看具体模块。先看厨房长什么样、做一道菜，最后才背菜谱。
2. **每个阶段必须动手** — 看代码和跑代码是两回事。每个阶段结尾有一条 `uv run` 操作指令，跑一遍比读三遍管用。
3. **略读数据模型，追请求时回查** — 第一次看 `sse_events.py` 只记类型名和字段名，不背定义。等追请求时看到 `constraints.budget_max` 影响了 SQL WHERE 子句，自然就记住了。
4. **测试是最好的规格说明书** — 学完一个模块后翻对应的 `tests/test_*.py`，比文档更精确地展示预期行为和边界条件。
5. **区分"复杂度"和"含金量"** — retriever 是算法最复杂的模块（810 行、12 步管线、多路融合），但 pipeline.py 的编排决策和铁律 3 的实现（消息规则优先于 LLM 调用）体现的工程判断力，才是这个项目真正和竞品拉开差距的地方。

> **时间说明**：各阶段标注的时间是经验值，实际因人而异。Java 后端转 Python 或对 FastAPI/异步编程不熟悉的读者，建议按 1.5× 预留。

## 阶段 1：跑起来，看一条请求的完整生命周期（1 小时）

**目标**：不看源码，先看行为。启动后端，发一条请求，看 SSE 事件流长什么样。

### 1.1 启动后端

> 如果已经通过 `docker-compose up` 启动了 Docker 环境，后端已在 8000 端口运行，跳过本节，直接进入 1.2。

```bash
cd backend
uv sync --extra dev
uv run uvicorn src.api.app:app --reload --port 8000
```

确认启动成功：浏览器打开 `http://localhost:8000/docs`，能看到 Swagger 页面。

### 1.2 发一条请求，观察 SSE 事件流

开两个终端窗口：

**终端 A**（后端日志）：
```bash
cd backend && uv run uvicorn src.api.app:app --reload --port 8000
```

**终端 B**（发请求）：
```bash
cd backend
uv run python ../scripts/chat_stream_demo.py "推荐适合油皮的洗面奶，200元以内"
```

观察终端 B 的 SSE 输出。重点关注：
- `thinking` 事件 — 出现在哪些阶段之间？
- `criteria_card` 事件 — `chips` 字段和 `constraints` 字段分别长什么样？`chips` 是前端展示的标签，`constraints` 是后端检索用的结构化条件，它们是什么关系？
- `product_card` 事件 — 每个商品带了哪些字段？`evidence` 数组里有什么？
- `text_delta` 事件 — 文案是流式推送的还是一口气返回的？
- `done` 事件 — 出现在最后，标志着本轮结束

### 1.3 略读 sse_events.py（15 分钟）

打开 `backend/src/types/sse_events.py`，带着刚看到的 SSE 输出对照读：

- 找到 `CriteriaPayload` 类 — 验证 `chips` 和 `constraints` 的类型定义
- 找到 `Constraints` 类 — 注意所有字段都是 `X | None`，没有 `dict[str, Any]`
- 找到 `ProductPayload` 类 — 验证商品卡片的字段
- 找到 `format_sse()` 函数 — 理解 SSE 事件的序列化格式
- 扫一眼 10 种 event type 的类名，不精读

**学到什么程度可以进入阶段 2**：能说出一个典型的推荐响应包含哪几种 SSE 事件类型，每种大概长什么样。`Constraints` 为什么不能用 `dict[str, Any]`（铁律 2）。

### 1.4 卡住了怎么办

| 现象 | 原因 | 解决 |
|------|------|------|
| `chat_stream_demo.py` 报 `Connection refused` | 后端没启动 | 确认 uvicorn 在跑，端口是 8000 |
| 返回 500 或全是 `error` 事件 | 大概率是 `.env` 未配置或 LLM API Key 不对 | 看终端 A 的 traceback；确认项目根目录有 `.env` 且 `DASHSCOPE_API_KEY` 有效 |
| SSE 输出只有 `error` 且后端日志有 `pgvector` 字样 | `DATABASE_URL` 指向了 SQLite 而不是 PostgreSQL | 确认 PostgreSQL 在运行，`.env` 中 `DATABASE_URL` 正确 |
| `uv sync` 报依赖冲突 | Python 版本不对 | 确认 `python --version` ≥ 3.12 |
| `chat_stream_demo.py` 找不到 | 路径问题 | 从 `backend/` 目录执行，脚本在项目根目录的 `scripts/` 下 |

## 阶段 3：LLM 调用层（1-2 小时）

**目标**：理解 task-oriented interface 设计——每个 LLM 任务是一个独立函数，返回 Pydantic model，调用方不需要知道底层是百炼还是 Doubao。理解 prompt 和代码的分界（铁律 3）。

阶段 2 追请求时，你在 `stages/intent.py` 中遇到了 `analyze_intent()`，在 `stages/recommendation.py` 中遇到了 `generate_criteria()`、`generate_recommendation()`、`generate_decision()`。你五次进入 `llm_client.py`。现在是时候系统地理解这一层的设计了。

```
llm_profiles.py  →  llm_gateway.py  →  llm_task_payloads.py  →  prompts.py  →  llm_client.py
```

| 顺序 | 文件 | 关注点 |
|------|------|--------|
| 1 | `backend/src/services/llm_profiles.py` | YAML 配置 → provider/api key/model 映射，`task_profile_names()` 返回 primary + fallback 列表 |
| 2 | `backend/src/services/llm_gateway.py` | OpenAI-compatible HTTP 传输层，primary 失败自动切 fallback |
| 3 | `backend/src/services/llm_task_payloads.py` | Prompt 消息构造 + JSON 解析 + payload 规范化（结构化输出边界） |
| 4 | `backend/src/services/prompts.py` | 运行时从 `backend/prompts/*.md` 加载 prompt 模板，硬编码字符串仅作 fallback |
| 5 | `backend/src/services/llm_client.py` | **门面**：5 个 task-oriented 接口 |

**5 个 LLM 任务接口**：

| 接口 | 返回类型 | Primary 模型 | 用途 |
|------|---------|-------------|------|
| `analyze_intent()` | `IntentResult` | Qwen-Turbo | 意图识别 + 约束提取 + 品类路由 |
| `generate_criteria()` | `CriteriaPayload` | Qwen-Turbo | 购买标准生成 |
| `generate_recommendation()` | `RecommendationResult` | Qwen-Turbo | 基于候选商品 + 证据生成推荐文案 |
| `generate_decision()` | `DecisionResult` | Qwen-Turbo | 最终决策生成 |
| `analyze_image()` | `ImageAnalysisResult` | Qwen-VL-Plus | 多模态图片理解 |

**铁律 4 的设计意图**：每个接口返回结构化的 Pydantic model，禁止返回 raw str 让调用方自己解析。这意味着：
- Runtime 层看到的是 `IntentResult`，不知道也不需要知道底层调用的是百炼还是 Doubao
- 更换模型只需要改 YAML 配置，不碰任何业务代码
- 每个接口有明确的输入输出契约，可以独立测试、独立 mock

## 阶段 4：深入检索管线（2-3 小时）

**目标**：理解 `retrieve_with_evidence()` 的 12 步管线，以及 7 个硬过滤函数的规则。理解检索管线和 LLM 调用层的关系——第 10 步的 Rerank 和第 12 步的证据绑定分别调用了阶段 3 学过的 `reranker.py` 和后续的证据服务。

检索是这个项目算法最复杂的模块，但不是含金量最高的模块——它的设计思路（混合检索 + 硬过滤 + 渐进放松 + 证据绑定）是信息检索领域的成熟做法。真正体现工程判断力的是阶段 2 的编排设计（pipeline.py）和阶段 3 的铁律 3/4 实现（prompt 边界 + task-oriented interface）。带着这个认知来读，把注意力放在**设计决策的边界**上——哪些逻辑代码化、哪些交给 LLM、为什么。

### 4.1 检索入口：retriever.py（60 分钟）

打开 `backend/src/services/retriever.py`，精读 `retrieve_with_evidence()` 函数，按以下 12 步逐段对照代码：

1. **缓存检查** — 基于 `CriteriaPayload + feedback` 的 TTL 缓存，图片检索跳过。为什么要区分文本和图片？
2. **查询 embedding** — `criteria_query_text(criteria)` → `embed_text()`。查询文本是怎么从 `CriteriaPayload` 构造出来的？
3. **并行图片召回** — 如果 `image_embedding` 存在，并行查 `product_image_embeddings` 表。为什么用 `asyncio.create_task` 而不是顺序执行？
4. **向量召回** — pgvector cosine distance 查询 → 7 个硬过滤函数逐商品检查 → `ProductHit` 列表
5. **渐进式放松** — 候选为 0 时：预算放宽 30% → 50% → 不限 → 移除 avoid_traits。**品类和子品类永不放松**——为什么？给用户看错误品类的商品比返回空结果更糟。
6. **BM25 召回 + RRF 融合** — BM25 关键词搜索 → RRF 合并向量排名和 BM25 排名。为什么需要 BM25？向量召回在什么场景下会失效？
7. **视觉召回合并** — 图片命中 → `ProductHit`，与文本命中去重合并（保留更高 vector_score）
8. **品牌偏好直取** — `brand_prefer` 非空时直接从商品目录拉取匹配商品。向量检索 + reranker 已经做了两次排序，为什么还需要这一步硬召回兜底？
9. **确定性排序** — `_rank_hits()`：`filter_score + vector_score - budget_penalty`。超预算的商品不是直接过滤而是加惩罚——为什么？
10. **Rerank 重排序** — qwen3-rerank API 精排 → 去重选 top_n。这是检索管线中唯一调用 LLM（rerank 模型）的步骤。对照阶段 3 的 `llm_gateway.py`，为什么 rerank 不走 `llm_client.py` 的 task-oriented interface？（因为它不是生成任务，是排序任务，走的是 `reranker.py` 自己的 gateway 封装）
11. **品牌偏好提升** — `_elevate_brand_preference()`：偏好品牌商品强制置顶。为什么 rerank 之后还要再做一次？
12. **证据绑定** — `_evidence_by_product()`：每个推荐商品附 1-4 条证据（why_buy > faq > risk > compare）
13. **缓存写入** — 文本查询结果写入缓存

### 4.2 检索底层工具（30 分钟）

| 顺序 | 文件 | 关注点 |
|------|------|--------|
| 1 | `backend/src/services/retrieval_features.py` | `criteria_query_text()`（标准 → 查询文本，品牌偏好时注入"必须优先推荐以下品牌"指令）、`product_document_text()`（商品 → 文档文本）、`product_match_score()`（确定性多维打分） |
| 2 | `backend/src/services/bm25_recall.py` | 启动时从 product_chunks 表构建内存 BM25 索引，jieba 分词搜索，搜索失败返回空列表（graceful degradation） |
| 3 | `backend/src/services/rrf_merge.py` | RRF 多路融合算法，仅 30 行纯函数：`score(d) = Σ 1/(60 + rank_i(d))` |
| 4 | `backend/src/services/reranker.py` | qwen3-rerank API 调用（百炼），输入 query + documents，返回按相关性排序的索引列表 |

### 4.3 硬过滤函数（15 分钟）

在 `retriever.py` 中找到 `_FILTER_CHECKS` 元组，逐个读：

| 过滤器 | 规则 | 为什么是代码不是 LLM |
|--------|------|---------------------|
| `_passes_feedback_product_filter` | 排除用户已拒绝的商品 ID | 精确 ID 匹配，LLM 做不了 |
| `_passes_category_filter` | 品类归一化后精确匹配 | 品类名有别名（"美妆护肤"/"美妆"/"护肤"），代码归一化，LLM 做不到一致 |
| `_passes_budget_filter` | 价格 ≤ budget_max 且 ≥ budget_min | 数值不等式，不是语义相似度 |
| `_passes_brand_filter` | 排除 brand_avoid 列表中的品牌（含别名匹配） | "日系"需要展开为具体的日本品牌名列表，代码查别名表 |
| `_passes_origin_filter` | 排除 origin_avoid 对应的品牌 | 同上，产地 → 品牌展开 |
| `_passes_product_type_filter` | 子品类归一化匹配（含层级包含匹配） | "裤子"应该匹配"户外裤"，代码 substring 匹配 |
| `_passes_avoid_trait_filter` | 排除含特定成分的商品（搜索商品全字段文本） | 在商品文本中精确查找"酒精""香精"等关键词 |

这些过滤器**全部是确定性代码**，不调 LLM。这就是铁律 3 的核心体现：路由逻辑和硬过滤条件必须代码化。Prompt 只做语言理解和生成。

### 5.3 入库与 Chunking

| 顺序 | 文件 | 关注点 |
|------|------|--------|
| 8 | `backend/src/services/chunking.py` | 商品 → 8 种语义 chunk（见下方速查表），每种标记 `retrieval_role` 和 `evidence_kind` |
| 9 | `backend/src/services/embedding.py` | 文本 embedding（qwen-text-embedding-v3, 1024 维） + 图片 VL embedding（qwen3-vl-embedding） |
| 10 | `backend/src/services/product_ingest.py` | 启动时数据入库全流程：读 JSON → chunk → embed → 写 DB |

**chunk 类型速查**：

| chunk_type | 来源 | retrieval_role | evidence_kind | 向量召回 | 证据绑定 |
|------------|------|---------------|---------------|---------|---------|
| profile | 商品属性拼接 | primary | profile | 参与 | 不参与 |
| marketing | 营销文案分段 | primary | why_buy | 参与 | 参与 |
| faq | 官方 FAQ（无风险词） | primary | faq | 参与 | 参与 |
| faq（含风险词） | 官方 FAQ（含警告） | risk | risk | **排除** | 参与 |
| positive_review | 好评（评分≥4） | evidence | why_buy | 参与 | 参与 |
| negative_review | 差评（评分≤2） | risk | risk | **排除** | 参与 |
| warning | 风险摘要 | risk | risk | **排除** | 参与 |
| compare | 对比轴文本 | evidence | compare | 参与 | 参与 |

**为什么差评和风险 chunk 虽然在向量召回阶段被排除，但仍然要入库？** 因为证据绑定阶段会用到——用户选中商品后可以看到风险提示，但差评内容不应该让一个商品被错误召回。

### 5.4 动手：看一条商品的 chunk 长什么样

用 SQLite 或 PostgreSQL 客户端打开数据库，执行：

```sql
SELECT id, product_id, chunk_index, 
       json_extract(metadata, '$.chunk_type') AS chunk_type,
       json_extract(metadata, '$.retrieval_role') AS retrieval_role,
       json_extract(metadata, '$.evidence_kind') AS evidence_kind,
       substr(chunk_text, 1, 100) AS text_preview
FROM product_chunks
WHERE product_id = 'P001'  -- 换成任意一个 product_id
ORDER BY chunk_index;
```

你会看到同一个商品的不同 chunk 如何按 retrieval_role 分类，以及 risk chunk 的文本内容和 primary chunk 的区别。

**学到什么程度**：能画出"100 条商品 JSON → chunk → embed → pgvector 索引"的完整数据流，并解释为什么差评 chunk 的 embedding 存在但不参与向量召回。

## 架构分层速查

```
┌────────────────────────────────────────────┐
│  API 层 (api/)                              │  ← HTTP/SSE 边界，不放业务逻辑
│  app.py / chat.py / cart.py / feedback.py   │
├────────────────────────────────────────────┤
│  Middleware (middleware/)                   │  ← 请求上下文传递
│  request_context.py                         │
├────────────────────────────────────────────┤
│  Runtime 层 (runtime/)                      │  ← 编排：只做调度，不放业务规则
│  pipeline.py / handlers.py / streaming.py   │
│  stages/ (intent/criteria/recommendation/…) │
├────────────────────────────────────────────┤
│  Service 层 (services/)                     │  ← 业务逻辑唯一存放处
│  llm_client / retriever / chunking / …      │
├────────────────────────────────────────────┤
│  Repo 层 (repos/)                           │  ← 持久化，不能 import service
│  database / models / products / documents   │
├────────────────────────────────────────────┤
│  Types & Config (types/ + config/)          │  ← 数据模型 + 配置，被所有层依赖
│  sse_events / schemas / settings / tuning   │
└────────────────────────────────────────────┘
```

依赖方向：**只能自上而下**（API → Runtime → Service → Repo → Types/Config）。`test_architecture_layers.py` 用 AST 扫描自动检查。

## 系统铁律

| 铁律 | 内容 | 违反后果 |
|------|------|---------|
| 铁律 1 | SSE event type 的 10 种是全集，新增必须三端对齐（contracts → Python → Android） | 前端解析崩溃 |
| 铁律 2 | `Constraints` 使用平铺字段 + `\| None`，显式枚举 | 检索硬过滤失效 |
| 铁律 3 | Prompt 只做语言理解/生成，路由和过滤必须代码化 | 不可调试的黑盒 |
| 铁律 4 | LLM 调用必须走 task-oriented interface，返回 Pydantic model | 调用方自行解析 raw str |
| 铁律 5 | 测试必须验证源码行为，禁止同义反复测试 | 装饰品测试，无防护价值 |
