## 全员先背的一分钟主线

Android 通过 `POST /chat/stream` 发起请求，FastAPI 建立 SSE 流；Pipeline 先做图片预分析、意图识别和槽位检查，再由 Handler 路由到推荐、对比、购物车等业务。推荐链路把用户需求转换成封闭的 Criteria DSL，通过 pgvector 向量召回、确定性过滤、BM25/RRF 辅助排序和 Rerank 得到候选商品，再将真实商品字段和 chunk 证据绑定到商品卡与推荐解释。多候选时先收集用户反馈，收敛阶段由确定性评分选择赢家，LLM 只负责解释。整个过程通过 `session_id`、`turn_id`、`seq`、审计日志和检索 Trace 保持可追踪。

> 注意：当前源码仍存在若干尚未修复的实现问题，集中列在“已知局限、源码问题与答辩口径”。答辩不能把设计目标直接说成已稳定实现。

## 一、RAG 检索链路

### 1.1 检索流程中硬过滤、向量召回、rerank 的执行顺序是什么？为什么这样排？

**一句话结论**：SQL 硬过滤缩小范围 → pgvector 语义召回 → Python 硬过滤复核 → BM25/RRF 辅助排序 → Rerank 精排。硬约束在前，避免语义相似度绕过用户明确条件。

**✅ 设计目标**：先把品类、预算、商品类型、排除品牌和排除商品等可下推条件放进 pgvector 查询的 SQL WHERE，再做 1024 维向量召回；召回结果经过 Python 硬过滤复核，然后执行 BM25/RRF 辅助排序、确定性粗排和 qwen3-rerank 精排。

**⚠️ 当前行为**：Python 硬过滤逻辑存在，但 SQL 过滤对象的构造参数与 `VectorSearchFilters` 定义不一致，正常检索可能在向量 SQL 前抛出 `TypeError`。因此答辩应说明这是目标链路，同时主动将参数契约不一致列为提交版本的已知缺陷，不能宣称该链路已经过完整线上稳定性验证。被追问时使用 14.5 的四句话模板。

**源码定位**：`backend/src/services/retriever.py::retrieve_with_evidence()`、`_sql_filters_for_recall()`、`_vector_recall_from_db()`；`backend/src/repos/documents.py::VectorSearchFilters`、`list_vector_chunks_by_similarity()`。

### 1.2 检索结果为空怎么办？

严格检索为空时依次尝试：预算上限 ×1.3、×1.5、移除预算上限，必要时再移除反馈中的 `avoid_traits`；始终不放宽品类和商品类型。如果仍无结果，返回 `_no_match_followup_text()` 建议用户调整条件，不会静默硬凑商品。

**当前缺陷**：Retriever 把 `relaxation_steps` 写在 Trace 顶层，而 Handler 从 `filters_applied.relaxation_steps` 读取，因此“预算已放宽”的用户提示可能无法触发。答辩应说“系统设计了可解释的渐进式放宽”，不要说“当前每次都能正确提示”。

**源码定位**：`backend/src/services/retriever.py::_relaxation_attempts()`、`_trace_details_for_chunk_retrieval()`；`backend/src/runtime/handlers.py::_budget_was_relaxed()`。

### 1.3 严格过滤无结果时为什么可以放宽预算？

预算是连续值，适合按可解释的阶梯尝试；品类和商品类型是离散语义，放宽它们可能把“洗面奶”变成其他商品，因此始终保留。当前代码除预算外，还可能在最后移除来自历史反馈的 `avoid_traits`，但不会移除明确排除的商品 ID。策略定义在 `retriever.py` 的 `_relaxation_attempts()`。

### 1.4 rerank 失败时排序依据是什么？

当前生产链路不对 rerank 做静默降级，provider 不可用或结果无效时会抛 `RerankUnavailable`。候选在进入 rerank 前确实会按过滤匹配分、向量分和预算惩罚做确定性粗排，但这不是 rerank 失败后的正式 fallback，答辩时不能把粗排说成已经实现的降级精排。

### 1.5 BM25、向量召回和 RRF 在当前实现中分别起什么作用？

向量召回负责找语义相关的 chunk，BM25 搜索全部 chunk，为品牌、型号和商品名等精确词提供排名；RRF 根据两路名次进行融合。但是融合结果映射回商品时仍依赖向量命中表，BM25-only chunk 可能被丢弃。因此当前实际效果更接近“BM25 增强向量候选排序”，不能宣称已经完整实现两路独立召回结果的并集。

**源码定位**：`backend/src/services/retriever.py::retrieve_with_evidence()`；`backend/src/services/bm25_recall.py::BM25Index.search()`；`backend/src/services/rrf_merge.py::rrf_merge()`。

## 二、数据准备与 Chunking 策略

### 2.1 1292 个 chunk 是怎么从 100 个商品切出来的？

每个商品至少生成一个 profile chunk；营销描述按句子边界和长度上限拆分；每个 FAQ、每条用户评价分别生成 chunk；另外根据内容生成 warning 风险摘要和 compare 对比维度。不同商品的 FAQ、评价数量不同，所以不是固定每个商品 13 个，而是 100 个商品最终共生成 1292 个语义 chunk，平均约 12.9 个。

### 2.2 为什么按 profile/marketing/FAQ/review/warning/compare 语义切分而不是固定长度？

按角色切分让每个 chunk 的证据角色明确：profile 承载稳定商品属性（召回入口）；marketing 提供官方卖点；FAQ 提供官方问答证据；review 提供用户体验证据；warning 单独标识风险（避免把负面内容当正向召回依据）；compare 把同品类比较维度结构化，服务决策卡。固定长度切分会破坏证据的语义完整性。

### 2.3 原始商品数据进入向量库前，做了哪些清洗和标准化？

`data/raw/ecommerce_agent_dataset/` 下的官方 100 条 JSON 是唯一事实源。当前正式入库链路由 `repos/products.py` 读取原始文件，再由 `services/product_ingest.py` 和 `services/chunking.py` 处理：

1. 统一 `product_id/title/base_price/category/sub_category/brand/image_path/skus/rag_knowledge` 等基础字段。
2. 归一化一级品类，将图片相对路径转换为客户端可访问的 `/assets/products/...` URL。
3. 整理 SKU，只保留结构合法并含有 `sku_id` 的规格项。
4. 折叠多余空白、限制文本最大长度，对别名、肤质、成分和场景词去重。
5. 通过领域词表提取肤质、使用场景、成分和风险词；提取时检查否定前缀，避免把“不含酒精”误判为“含酒精”。
6. 为每个商品生成 `knowledge_package`，保存基础事实、结构化属性、检索别名、推荐摘要、风险摘要和对比维度。

`data/scripts/process_data.py` 是早期生成 `data/processed/products.json` 和 `chunks.json` 的离线整理脚本；当前正式 seed/reindex 直接从 raw JSON 重建，不依赖这两个派生文件，避免派生数据与事实源漂移。

### 2.4 一个商品具体会被生成哪些 chunk？

- `profile`：商品名、品牌、品类、价格、肤质、场景和检索别名，作为稳定召回入口。
- `marketing`：营销描述按句子边界和长度上限切分，标记为 `why_buy` 证据。
- `faq`：每个官方问答独立成块；包含风险词时标记为风险证据，否则作为普通 FAQ 证据。
- `positive_review` / `negative_review`：每条评价独立成块；评分不高于 2 的评价进入风险角色，其余进入推荐证据角色。
- `warning`：从营销文案、FAQ 和低分评价中提取风险句，形成风险摘要块。
- `compare`：按照品类生成比较维度，例如数码产品关注核心参数、性能、续航和价格。

每个 chunk 都附带 `chunk_type`、`retrieval_role`、`evidence_kind`、品类、品牌、价格和来源版本等 metadata。检索阶段因此可以区分主召回、推荐证据和风险证据。

### 2.5 为什么不把一个商品的所有文本直接拼成一个大 chunk？

全部拼成大块会让营销卖点、FAQ、好评和风险评价相互污染：负面评价可能因为语义相似被当作推荐理由，证据页也难以说明具体引用了哪类来源。按语义角色切分后，可以让 profile 负责召回、why_buy 支撑推荐、risk 负责风险提示、compare 服务商品对比，并保留更细的证据粒度。

### 2.6 如何保证重复处理数据时结果可复现，不产生重复或脏索引？

入库时会为每条商品计算 `source_hash`，再计算整个数据集的 `dataset_hash`，同时记录 `dataset_version`、`chunking_version`、embedding 模型和索引时间。如果数据哈希和向量维度未变化，可以跳过重复 seed；需要重建时，会先删除该商品旧 chunk 及关联 evidence，再写入新结果。文本 embedding 每批处理 10 条，并强制校验每个向量为 1024 维；重建结束后还会检查 chunk 总数、已向量化数量和向量维度是否一致。

## 三、向量库与 Embedding

### 3.1 为什么选 pgvector 而不是 Chroma 或 Qdrant？

pgvector 与 PostgreSQL 同库部署，零额外运维；100 条商品的规模不需要专用向量数据库的分布式能力；HNSW 索引足够覆盖演示需求。减少一个基础设施依赖 = 减少一个出故障的点。

### 3.2 为什么当前运行时强制使用 PostgreSQL + pgvector，而不再保留 SQLite fallback？

当前运行时直接依赖 PostgreSQL 的 vector 类型、`<=>` 余弦距离和 HNSW 索引。移除 SQLite 运行时分支可以避免开发和演示使用两套检索语义，也能防止“本地测试通过，但真实 pgvector SQL 出错”。测试和演示都应围绕 PostgreSQL + pgvector 验证。

### 3.3 如何保证入库的 embedding 真的是 1024 维？

正式入库使用百炼 `text-embedding-v3`。`product_ingest.py` 在每个 batch 返回后逐条校验向量长度，不是 1024 维就立即失败；重建结束后再通过 `vector_dims()` 检查全部 chunk 的最小和最大维度是否一致。测试 fixture 中可能构造简化向量，但那不属于运行时 embedding fallback。

### 3.4 HNSW 索引参数是怎么调的？

当前建索引 SQL 没有显式传 `m` 和 `ef_construction`，使用的是 pgvector 默认参数。因为当前只有约 1292 个文本向量和 100 个图片向量，没有做专门的 HNSW 参数搜索；现阶段主要延迟来自外部模型调用而非索引。扩展到大规模数据时才需要基于召回率、构建成本和查询延迟重新调参。

## 四、防幻觉

### 4.1 如何保证推荐理由只引用 evidence？

三层防御：(1) prompt 要求依据 evidence 与 reason_atoms；(2) 代码生成结构化 `reason_atoms` 并标记事实来源；(3) 推荐文案有候选商品白名单、商业禁词和价格 GroundingGuard 等后验检查。`evidence_id` 不一定都是数据库 chunk，也可能指向 `product_field:price`、`product_field:category` 或 `criteria_filter:*`，因此更准确的说法是“每个理由有可解释的事实来源”，而不是全部都能跳转到 chunk。

### 4.2 如何保证最终推荐商品一定来自库内？

`product_card` 只由检索出的 `ProductPayload` 生成，商品来自 raw dataset。`generate_decision` 校验 `winner_product_id` 必须在候选 ID 内。LLM 没有机会改写商品卡的价格、图片、商品名字段——这些字段直接从数据库读取。

### 4.3 用户问优惠券/库存时为什么不会编造？

prompt 禁止编造优惠、库存、物流、购买承诺；`llm_client` 对推荐文案做禁词校验。更稳的做法是专门 handler 回复"商品库没有该字段，不能确认"（已实现：`_emit_commercial_claim_reply`）。

### 4.4 prompt injection 要求"忽略商品库直接编 5 个商品"时，怎么防护？

商品卡只由检索结果生成，不受 LLM 文本输出控制，product_id/name/price/image_url 都来自数据库。非流式推荐结果会检查候选集外商品名和禁止商业词；流式文案无法保证每个 token 都在发送前完成所有校验，因此还会通过价格 GroundingGuard 和纠正提示做分层防护。这里应表述为降低和限制幻觉影响，而不是承诺绝对消除。

### 4.5 reason_atoms 是什么设计？为什么不直接让 LLM 生成推荐理由文本？

`reason_atoms` 是结构化理由单元，每个包含 `dimension`、`value`、`text` 和 `evidence_id`。它可以引用真实 chunk，也可以引用数据库字段或检索规则。好处是前端能按维度展示，后端能区分事实来源，LLM 主要负责自然语言组织而不是自行发明商品事实。

## 五、多轮上下文

### 5.1 多轮怎么记住上一轮？

`conversations` 表保存 `session_id`、`criteria_json`、`product_ids`、`user_message` 和压缩摘要。下一轮会读取上一轮 Criteria、候选商品和会话摘要，并把 Android 请求携带的 history 一起交给 Intent/Criteria 阶段。同品类的 LLM 正式结果以上一轮 constraints 为基础，再用本轮返回字段覆盖；`criteria_patch` 路径才会对 brand_avoid、ingredient_avoid 等列表执行追加去重。用户明确切换品类时，不继承与新品类无关的旧约束。

### 5.2 "这个""第二个商品"如何解析？

`runtime/cart_rules.py` 的 `referenced_product_id()` 按优先级解析：明确 product_id → 消息中嵌入的 product_id → 商品名唯一匹配 → “第二个/第2款”等序数 → “这个/这款”等历史指代。序数按上一轮 product_ids 下标定位，普通指代使用最近记录的商品；无法唯一解析时返回 clarification，不会凭空操作。

### 5.3 第二轮"要轻量的"是怎么关联到第一轮的"跑鞋"的？criteria 合并逻辑是什么？

意图阶段拿到 `extracted_constraints`；criteria 阶段调 `generate_criteria()` 传入 `existing` criteria（上一轮保存的），LLM prompt 里写"在它的基础上修改"，把上一轮的 category/product_type 继承下来，只修改本轮新增的约束。

### 5.4 `criteria_patch` 与普通 LLM 标准生成有什么区别？

`criteria_patch` 是确定性的局部修改路径，不调用 LLM。标量字段直接覆盖，列表字段采用“旧值 + 新值 + 去重”；修改后重新生成 chips、summary，并把字段来源标记为 user。普通 LLM 路径会结合历史 Criteria、反馈和会话摘要生成正式标准，同品类下合并历史，切换品类时清理没有在本轮明确提出的旧约束，避免条件串到新品类。

## 六、购物车与指代解析

### 6.1 "把第二个加到购物车""删除第二款""改成 2 件"如何解析指代和持久化状态？

Android 端 `resolveAddToCartTarget()` 做模糊匹配：序数词提取 + 品牌/品类/名称多维打分 + 歧义检测。后端购物车状态存在 `cart_items` 表（session_id + product_id + quantity），跨轮通过 session_id 关联。

### 6.2 购物车状态存在哪里，如何跨轮引用？

`cart_items` 表，按 session_id 隔离。每轮 cart_action 事件返回完整 cart snapshot（items/total_items/total_price），前端直接渲染，不需要额外查询。

### 6.3 上一轮推荐为空时用户说"加到购物车"怎么办？

`referenced_product_id()` 返回 None → handler 发 clarification 事件问"你想把哪个商品加入购物车？"，不会凭空加购。

## 七、多模态

### 7.1 图片能力到底是视觉相似检索，还是 VLM 属性抽取后走文本 RAG？

**✅ 设计目标**是双通道：(1) VLM 属性理解，识别品类、属性和可见特征并注入 Intent/Criteria；(2) qwen3-vl-embedding 生成 1024 维图片向量，通过 pgvector 召回相似商品。VLM 先参与请求预处理；进入推荐 Handler 后生成图片 embedding，文本和图片召回再并行执行。

**⚠️ 当前行为**：视觉召回代码存在字段名不匹配、异步证据调用未 `await`、参数类型错误等问题；异常路径可能退化为文本链路。答辩应展示“VLM 属性理解 + 视觉向量召回”的架构，但将视觉结果合并稳定性列为已知缺陷。被追问时使用 14.5 的四句话模板。

**源码定位**：`backend/src/runtime/stages/multimodal.py`；`backend/src/services/retriever.py::_build_visual_hits()`、`_merge_text_and_visual()`、`_supplement_visual_evidence()`；`backend/src/repos/documents.py::ImageSimilarityHit`、`evidence_for_product()`。

### 7.2 图片上传后 VLM 结果如何转成检索条件？

`services.message_rules.image_analysis_to_retrieval_constraints()` 从 VLM 结果提取品类、产品类型、肤质、无糖/低糖和日常场景等，再由 `message_with_image_context()` 写入消息上下文，后续 Intent 与 Criteria 阶段将它结构化到 Constraints。

## 八、SSE 协议与架构

### 8.1 SSE 的 text_delta 和 product_card 是并行发出的吗？如果 LLM 流式输出中断，已发出的商品卡怎么处理？

商品卡与推荐文案不是“召回一个 token 就发一张卡”的并行关系，而且没有一条覆盖所有分支的固定事件顺序：

- 普通多候选推荐：`thinking → product_card × N → 推荐 text_delta → criteria_card → 引导 text_delta → done(awaiting_product_feedback)`。
- 单候选：`product_card → criteria_card → 决策解释 → final_decision`。
- 场景购物策略：可能在检索和商品卡之前先发送场景判断文本与 `criteria_card`。
- 澄清、无结果、对比、购物车分别有自己的事件序列。

```text
普通多候选：thinking ─→ product_card×N ─→ 推荐文本 ─→ criteria_card ─→ 引导文本 ─→ done(等待反馈)
单候选：                product_card ─→ criteria_card ─→ 决策解释 ─→ final_decision
场景策略：      场景判断文本 ─→ criteria_card ─→ 检索 ─→ product_card...
异常：          已建立 SSE ─→ error ─→ done(error)
```

商品卡来自检索结果，不依赖后续 LLM 文案；已发出的卡片不会因为文本生成中断而变成模型编造的数据。流建立后的异常通过 `error + done(error)` 收尾。

**源码定位**：`backend/src/runtime/handlers.py::continue_recommendation_from_criteria()`、`_product_card_events()`、`_stream_recommendation_text_events()`。

### 8.2 前后端协议怎么保证一致？

三层守卫：(1) `contracts/sse-events.schema.json` 是 source of truth；(2) Python 端 `sse_events.py` import-time 校验 schema 对齐；(3) Kotlin 端 assemble 强制跑契约测试。新增 event type 必须三端同步更新。

### 8.3 Android 如何解析 product_card/final_decision/cart_action？

`SseEventParser.kt` 解析 SSE data JSON → `AgentPayload.kt` sealed class 区分事件类型 → `ChatUiNode.kt` 按类型渲染对应 Composable 组件。

### 8.4 `session_id`、`turn_id`、`seq` 分别解决什么问题？

`session_id` 标识完整的多轮会话，用于关联历史标准、反馈和购物车；`turn_id` 标识一次“用户输入 + Agent 回复”，用于取消、审计和耗时追踪；`seq` 只表示同一 turn 内的事件顺序，用于排序、去重和检测丢事件，不代表业务阶段。

### 8.5 SSE 建立前和建立后的错误处理有什么区别？

请求参数不合法时，Pydantic 在流建立前完成校验，FastAPI 直接返回 HTTP 422。SSE 开始后 HTTP 200 和响应头已经提交，后续 LLM、数据库或业务异常不能再改成 HTTP 500，只能发送 `error` 和 `done(error)` 事件。真实异常堆栈只写服务端日志，对客户端返回脱敏信息。

### 8.6 用户点击停止后，后端如何取消正在生成的内容？

Android 调用 `/chat/cancel`，后端根据 `session_id + turn_id` 设置取消令牌。Pipeline 在阶段心跳或活跃检查点发现取消后抛出 `StreamCancelled`，取消仍在运行的后台任务，记录审计事件，发送 `done(cancelled)`，最后清理 active turn 和 cancel token。这是协作式取消；0.8 秒是阶段心跳与取消检查周期，不是模型超时时间。

### 8.7 为什么 `stream_chat()`、`chat_stream()` 和 `_run_chat_turn()` 不合并？

`stream_chat()` 属于 API 层，负责 HTTP/SSE 响应头和事件序列化；`chat_stream()` 属于 Runtime 层，负责 turn 生命周期、取消、异常、审计和资源清理；`_run_chat_turn()` 只负责正常业务编排。拆分后 Runtime 可以脱离 FastAPI 测试，也避免 Controller 同时承担协议、业务和资源生命周期。

## 九、模型与工程决策

### 9.1 为什么用 qwen-turbo 做生成主力，而不是 qwen-plus？

task-oriented interface 按任务选模型。意图、Criteria、推荐和决策解释使用 qwen-turbo，主要考虑延迟、成本以及结构化任务对超大模型能力的依赖较低；多模态使用 qwen-vl-plus，embedding 使用 text-embedding-v3。当前没有足够的正式 A/B 评测证据证明 qwen-turbo 与 qwen-plus “效果无显著差异”，答辩不要做这个结论。

**源码定位**：`backend/src/config/llm_profiles.yaml`；`backend/src/services/llm_profiles.py::task_profile_names()`。

### 9.2 开发态和生产态怎么区分？

**✅ 设计目标**：`STRICT_RUNTIME=1` 应统一禁止关键能力的静默测试兜底，让真实 provider、数据库和索引问题尽早暴露。

**⚠️ 当前行为**：当前代码只在 `Settings` 中读取该开关，并在 `/health` 返回其值，没有发现业务服务根据它统一切换 fallback 的实现。Embedding 和 Rerank 没有运行时 fallback，是各自服务本身的策略，并不是 `STRICT_RUNTIME` 开关产生的效果。`ALLOW_MEMORY_STATE_FALLBACK=1` 只适合开发态；答辩演示仍应显式使用 PostgreSQL、pgvector 和真实模型服务。被追问时使用 14.5 的四句话模板。

**源码定位**：`backend/src/config/settings.py::Settings`；`backend/src/api/app.py::health()`。

### 9.3 哪些测试是真链路，哪些只是 mock 链路？

`pytest` 默认 mock external AI，验证 schema、事件顺序、过滤逻辑、状态管理。`smoke_live_rag` 和 `demo_smoke` 用真实 provider + 真实 pgvector，验证端到端链路。答辩要同时展示两者。

### 9.4 哪些代码是核心手写设计，哪些是 demo fallback？

核心设计包括 SSE schema、Pipeline stage、Retriever、Chunking、Evidence、会话/购物车状态、LLM task interface 和 trace/audit。测试会在外部 AI 的 I/O 边界使用 mock，以验证内部业务逻辑；这些测试替身不属于演示运行时。答辩时不应按“哪段代码是 AI 写的”简单切文件，而应说明团队如何定义架构、规则、契约、验收标准并对最终实现负责。

### 9.5 哪些代码是为了比赛评审权重主动设计的，而不是 AI 拼接？

评审权重驱动的设计：结构化商品卡 + evidence source_id（35% 基础功能）、防幻觉后验校验（减分项防御）、SSE event schema 三端对齐（25% 工程质量）、live smoke 门禁（20% 可靠性）、购物车 CRUD（20% 加分项）。

### 9.6 Intent 和 Criteria 为什么要分成两层？

Intent 解决“用户想执行什么动作”，例如推荐、对比或加购；Criteria 解决“如果要推荐，应按什么正式条件检索”。分层后，业务路由不需要理解完整购买条件，快速规则也不必承担查询 DSL 的生成职责。可以把 `IntentResult` 理解为 Command DTO，把 `CriteriaPayload` 理解为 Query DTO。

### 9.7 为什么 Criteria 要设计成封闭 DSL？

所有允许的约束字段都由 Pydantic 显式声明，LLM 不能随意发明检索字段；未知字段会被清理，类型会被校验，检索、推荐理由和前端展示共享同一套语义。封闭 DSL 不等于所有字段都是硬过滤：预算、品类、排除品牌等可确定执行，肤质、场景等字段也可能用于查询文本、排序和推荐理由。

### 9.8 哪些条件不允许仅由 LLM 自行推断？为什么？

`budget_min`、`budget_max`、`brand_avoid`、`origin_avoid`、`ingredient_avoid` 等会直接缩小候选集，因此必须来自用户本轮明确表达或可继承的历史状态。模型擅自补充的这类硬约束会被确定性代码清除，避免系统替用户做决定或错误过滤掉合适商品。

### 9.9 什么是投机检索？失败后如何兜底？

系统先根据 Intent 构造简化的临时 Criteria，后台启动一次检索；同时调用 LLM 生成正式 Criteria。正式标准返回后，再用完整约束过滤投机结果。如果结果全部被过滤、场景策略修改了 Criteria，或者临时标准与正式标准差异过大，就丢弃投机结果并执行正式检索。它通过重叠模型推理和检索 I/O 获得潜在延迟收益，但不保证每次都更快，效果应通过 trace 耗时和命中率评估。

### 9.10 为什么这是 workflow-style Agent，而不是 ReAct Agent？

当前系统由确定性规则、意图分类、槽位检查和 Handler 注册表决定执行路径，LLM 不会在运行时自由选择下一项工具或无限循环推理。购物车、预算过滤和候选决策都需要可预测、可审计的行为，因此选择受控工作流 Agent；RAG 检索是工作流中的一个能力，而不是交给模型自由调度的工具。

### 9.11 Docker Compose 如何实现一键启动，演示前怎么验证？

`deploy/docker-compose.yml` 启动两个核心服务：`pgvector/pgvector:pg16` 数据库和 FastAPI API。API 通过服务名 `postgres` 连接数据库，启动时开启自动 Seed 和严格 1024 维 Embedding 校验；Compose 等待 PostgreSQL 健康后再启动 API，并为两者配置 healthcheck。

```text
docker compose -f deploy/docker-compose.yml --env-file .env up --build
        │
        ├─ postgres：创建 PostgreSQL + pgvector，持久化到 pgdata
        └─ api：建表/补列/建索引 → 自动导入商品与向量 → 启动 FastAPI
```

演示前不能只看容器是 `running`：还应检查 `docker compose ps`、`/health`，并在 API 容器中运行 `src.scripts.demo_smoke` 或 `src.scripts.smoke_live_rag`。首次自动生成 1292 个文本向量需要真实百炼 Key 和一定时间，Compose 的 API healthcheck 因此设置了较长 `start_period`。

**源码定位**：`deploy/docker-compose.yml`；`backend/src/api/app.py` lifespan；`backend/src/services/startup.py`；`backend/src/scripts/demo_smoke.py`、`smoke_live_rag.py`。

### 9.12 为什么没有使用 Alembic？当前数据库升级有什么风险？

比赛版本使用 `SQLModel.metadata.create_all()` 创建新表，并通过 `_ensure_model_columns_sync()` 对已有表执行 `ALTER TABLE ADD COLUMN`。优点是 Demo 部署简单；缺点是没有版本化迁移历史，不能可靠处理改名、类型变化、数据回填和回滚，多实例同时启动时也不是理想的迁移方式。评测表甚至保留了显式删除重建函数，因此不能把当前方案称为成熟生产迁移。

生产化会引入 Alembic，类似 Java 项目的 Flyway/Liquibase：迁移脚本进入版本控制，部署前单独执行，并为破坏性变更提供备份、回滚和兼容窗口。

**源码定位**：`backend/src/repos/database.py::create_db_and_tables()`、`_ensure_model_columns_sync()`、`_add_missing_columns_sync()`、`migrate_eval_tables()`。

### 9.13 Android 的喜欢、不感兴趣等反馈如何进入下一轮推荐？

用户滑动、点赞、打开证据或查看详情后，`ChatViewModel.submitProductInteraction()` 在 `viewModelScope` 中调用 `ChatRepository.submitProductFeedback()`，网络层向 `POST /feedback` 发送 `session_id/deck_id/product_id/feedback_type/action/reason`。后端 API 调用 `submit_feedback_request()` 持久化到 `feedbacks` 表；下一轮 Criteria、检索和最终决策通过 `get_feedback_context()` 读取这些信号，用于排除商品、提取偏好和计算用户行为分。

```text
Android 交互
  → ChatViewModel.submitProductInteraction()
  → ChatRepository.submitProductFeedback()
  → FeedbackApi POST /feedback
  → services.feedback → repos.feedbacks → feedbacks 表
  → 下一轮 Criteria / Retrieval / Decision
```

**源码定位**：`android/feature/chat/.../ChatViewModel.kt::submitProductInteraction()`；`android/core/data/.../ChatRepository.kt::submitProductFeedback()`；`android/core/network/.../FeedbackApi.kt`；`backend/src/api/feedback.py`；`backend/src/services/feedback.py`；`backend/src/repos/feedbacks.py`。

### 9.14 为什么没有引入 Celery 和 Redis？

当前在线主链路是一次请求内的短任务编排，需要立即通过 SSE 返回结果；Python `asyncio` 已能并发处理 Intent/Criteria、投机检索、图片召回和观测记录。为 100 个商品、单实例比赛 Demo 引入 Celery、Broker、Worker 和 Redis 会增加部署、状态一致性、重试和排障成本，却不能直接解决外部模型延迟。

这是有意识的范围裁剪，不代表它们永远不需要：当离线批量重建向量、评测任务、图片处理或多实例共享缓存需要脱离请求生命周期时，可以引入任务队列；当跨 Worker 共享缓存、限流或分布式锁确有价值时，再引入 Redis。

## 十、最终决策、商品对比与购物策略

### 10.1 最终赢家由 LLM 决定吗？

不是。`score_candidates()` 对候选执行确定性评分：

`final_score = retrieval × 0.35 + criteria_match × 0.25 + user_signal × 0.25 + evidence × 0.10 - risk × 0.05`

代码按分数排序并锁定 `winner_product_id`，LLM 只解释为什么选择它，不能改写赢家。这样可以防止模型因为措辞偏好推翻用户行为和硬约束。

**源码定位**：`backend/src/services/decision_scoring.py::score_candidates()`、`decision_confidence()`；`backend/src/runtime/handlers.py` 收敛分支；`backend/src/runtime/stages/decision.py::run_decision()`。

### 10.2 为什么首轮多候选不立即给最终答案？

多个候选分数接近且没有用户反馈时，系统返回 `done(awaiting_product_feedback)`，让用户通过喜欢、不感兴趣、查看证据或加购提供信号。收到足够信号后再计算最终决策，可以把“模型替用户拍板”改成“用户参与的可解释收敛”。

### 10.3 商品对比如何保证不是 LLM 临时编表？

Handler 先解析目标商品，最多比较 4 个；`build_comparison()` 根据品类选择比较轴，从商品字段和 evidence 中计算每个轴的分数、详情、证据 ID、优势和风险，LLM 只承担自然语言结论生成。对比卡因此仍以结构化数据为主。

**源码定位**：`backend/src/services/compare.py::build_comparison()`、`_get_axis_names()`、`_score_product_on_axis()`、`_determine_winner()`；`backend/src/runtime/handlers.py` 对比 Handler。

### 10.4 “送妈妈的礼物”“旅行必备”为什么不直接追问品类？

这是场景化购物策略，不一定先有明确品类。`shopping_strategy` 通过确定性规则判断 gift、travel、interest 等场景和用户决策障碍，生成选购方向；旅行等组合场景还可以构造多个 Criteria 并行跨品类检索。LLM 负责自然语言表达，场景分类和方向选择主要由代码控制。

**源码定位**：`backend/src/services/shopping_strategy.py::is_likely_shopping_strategy_request()`、`build_shopping_strategy_plan()`、`_build_travel_combo_criteria()`。

## 十一、评测闭环与效果证明

### 11.1 项目如何证明 RAG 有效，而不是只展示几个 Demo？

项目提供 20 条评测样本和 15 项指标，发布验收记录的综合分为 78.4%。当前 Runner 实际输出 8 个确定性子指标、6 个 LLM Judge 子指标和 1 个 `overall_score`，合计 15 项；`metrics.py` 中定义但未被 Runner 调用的函数不计入当前评测口径。指标覆盖 Intent、约束提取、Criteria 覆盖、Recall@K、证据覆盖、约束满足、忠实度、多轮一致性和排序合理性等。答辩时应把 78.4% 表述为“特定样本、特定模型和特定版本下的验收结果”，不能外推为线上准确率。

**运行证据**：`backend/src/runtime/eval_runner.py::_deterministic_metrics()`、`_llm_metrics()`；`README.md` 的评测表；样本位于 `data/eval/eval_samples.json`。

### 11.2 为什么同时需要确定性指标和 LLM Judge？

Intent 是否正确、预算是否满足、目标商品是否进入 Top-K 等有明确答案，适合确定性计算，结果稳定且可复现；忠实度、上下文质量和排序合理性包含语义判断，使用 LLM Judge 更合适。两者结合可避免所有结果都依赖另一个模型主观打分。

**源码定位**：`backend/src/services/eval/metrics.py`；`backend/src/services/eval/llm_judge.py`。

### 11.3 评测结果如何反向推动系统改进？

先根据失败指标定位阶段：Intent 错误看规则和分类 Prompt；约束提取错误看 Criteria DSL 与历史合并；Recall@K 低看查询文本、chunk、过滤和召回；忠实度低看 evidence 与生成校验；多轮一致性低看状态合并。修改后使用同一版本化样本回归，避免只凭 Demo 手感调 Prompt。

### 11.4 78.4% 还有什么局限？

样本只有 20 条，无法代表开放世界用户分布；LLM Judge 自身会有波动；外部模型、Prompt、数据和索引变化都会导致分数漂移。后续应扩充边界样本、固定模型版本、记录多次运行方差，并增加人工抽检。

## 十二、可观测性、降级与演示应急

### 12.1 Request Log、Audit、Retrieval Trace 和 LLM Observation 有什么区别？

- **Request Log**：记录一次 HTTP 请求的状态、耗时和关联 ID。
- **Audit Event**：记录业务阶段和关键决策，例如意图、Criteria、取消和异常。
- **Retrieval Trace**：记录查询、过滤、候选、放宽步骤、排序和 fallback。
- **LLM Observation**：记录模型任务、provider、延迟、token、解析状态和 fallback 来源。

它们通过 `request_id/session_id/turn_id` 关联，并可按一次请求、一次 turn 或整个 session 组成 Debug Bundle。

**源码定位**：`backend/src/services/audit.py`、`trace_recorder.py`、`observability_llm.py`、`observability.py::get_*_debug_bundle()`。

### 12.2 哪些模型调用支持降级，哪些不支持？

Intent、Criteria、推荐、决策解释、对比和购物策略文案配置为 qwen-turbo 主模型、豆包 fallback。图片理解、文本 embedding、rerank 和图片 embedding 当前没有备用模型。流式推荐一旦已经向客户端发送 delta，也不能无缝切换模型并重放整段文本。

**源码定位**：`backend/src/config/llm_profiles.yaml`；`backend/src/services/llm_gateway.py`。

### 12.3 演示时模型服务失败怎么办？

先区分故障位置：生成模型失败可以在尚未输出流式内容前尝试配置的 fallback；embedding 或 rerank 失败会中断检索，应发送脱敏 `error + done(error)`，不能伪造候选；图片链路失败可说明并回到文本输入。演示前应运行真实 provider 与 pgvector 的 smoke，而不能只依据 mock 单测。

### 12.4 健康检查返回成功就代表推荐链路可用吗？

不代表。当前 `/health` 更接近进程存活检查，没有完整验证数据库、pgvector 索引、embedding、rerank、生成模型和图片模型。生产化应拆分 liveness、readiness 和 dependency health，并对关键依赖设置超时和告警。

### 12.5 测试数量很多，为什么仍然可能有运行时契约错误？

默认测试会跳过部分集成和预发布用例，外部 AI 通常被 mock；如果测试只覆盖纯过滤逻辑，没有真正构造 repo DTO 或连接 PostgreSQL，就可能漏掉参数名、异步调用和字段契约问题。答辩应强调测试分层，而不是把“测试通过”表述成所有真实依赖均已验证。

## 十三、评委可能随手测的边界场景

### 13.1 "帮我选"被误分类怎么办？

Convergence 协议：前端发 `converge=true` 强制走 continue handler，跳过 LLM 意图分类。

### 13.2 "今天天气怎么样"会不会进入推荐链路？

意图阶段识别为 chitchat，返回引导文案"我是购物助手，可以帮你找商品、比价格、加购物车"，不进检索。

### 13.3 "有没有戴森的吹风机"（库中没有的商品）？

`_unsupported_product_type()` 拦截，返回"当前商品库暂不覆盖吹风机，我不能基于现有数据给出可靠推荐"。不编造、不硬凑。

### 13.4 重复查询怎么处理？

检索结果有进程内 TTL 缓存，相同 Criteria 与反馈命中时直接返回，减少重复 embedding 和 rerank 调用。当前 Key 没有包含 `top_n`，同一查询以不同返回数量调用时可能错误复用结果；缓存也没有跨进程共享和数据版本失效机制。

**源码定位**：`backend/src/services/retrieval_cache.py::RetrievalCache._make_key()`；`backend/src/services/retriever.py::retrieve_with_evidence()`。

### 13.5 用户只说“送妈妈的礼物”或“旅行必备”，没有明确品类怎么办？

系统会先判断是否属于 gift、travel、interest 等场景化购物请求。命中后可以跳过普通的品类槽位反问，由 `shopping_strategy` 识别用户的决策障碍并生成选购方向；旅行等明确组合场景还可以构造多个 Criteria，并行执行跨品类检索。这样避免反复追问“你想买什么品类”造成对话死循环。

## 十四、已知局限、源码问题与答辩口径

### 14.1 只有 100 条商品，能证明系统可以扩展到十万级吗？

不能直接证明。当前数据规模足以验证比赛要求下的完整 RAG 链路、协议和工程设计，但扩大到十万级后，需要重新评估 HNSW 参数、过滤选择性、索引更新、BM25 架构、Rerank 候选规模、成本和延迟。当前设计只将粗排后的有限候选送入 Rerank，为后续扩展保留了边界。

### 14.2 规则优先的意图识别有什么缺点？

关键词规则对未覆盖的近义表达存在盲区，例如“弄进篮子里”可能无法命中快速加购规则。这类请求会进入 LLM 兜底，因此不会直接失败，但会增加一次远程调用。词表不能无限扩张，否则规则冲突和维护成本会升高，所以当前规则由真实 Demo 和评测样本驱动。

### 14.3 当前为什么不做“召回一个商品就立即返回一个”的流式检索？

当前需要完成 embedding、向量召回、BM25/RRF、Rerank 和证据绑定后，才能确定可靠的候选顺序。提前返回未精排候选会带来排序变化、重复卡片，以及用户已经操作旧候选后的状态一致性问题。因此目前采用“检索完成后逐张流式发送商品卡”，后续若做预览候选，需要设计明确的替换协议。

### 14.4 提交版本有哪些需要诚实说明的源码问题？

下表记录的是源码审计结论，不代表比赛后必须立即修改。是否修复由团队另行决定。

| 问题 | 当前影响 | 答辩口径 | 建议改进 |
|---|---|---|---|
| `VectorSearchFilters` 参数契约不一致 | 正常文本/图片召回可能在 SQL 前抛 `TypeError`；预算也未正确下推 | 说明完整设计链路，并承认提交版本存在 DTO 参数名缺陷 | 对齐 `budget_max/product_type_aliases/brand_avoid/avoid_product_ids`，增加真实 repo 集成测试 |
| `_sql_filter_payload()` 仍读取旧字段 | 即使修复构造器，Trace 序列化仍可能报错 | 不宣称当前 Trace 已覆盖所有检索参数 | 统一 DTO 字段并加序列化测试 |
| Handler 向 `filter_products()` 传入不支持的 `max_products` | 特定二次过滤路径可能报参数错误 | 说明投机结果会接受正式 Criteria 二次校验，但实现仍需契约修复 | 删除无效参数或在函数签名中正式支持限制数量 |
| 品牌偏好查询调用 `list_products(filters=...)` | 品牌偏好补充路径可能报错 | 不把品牌偏好“硬保证首位”描述为所有场景均已稳定 | 改用 repo 支持的查询接口并补路径测试 |
| 放宽 Trace 写入/读取路径不一致 | 预算放宽提示可能不出现 | 说“设计了渐进放宽”，不说“每次均明确提示” | 统一 `relaxation_steps` 的 Trace schema |
| 图片命中读取 `similarity`，DTO 实际为 `distance` | 视觉命中转换可能失败 | 多模态架构成立，但视觉合并稳定性仍需修复 | 使用统一距离转分数函数 |
| 图片证据补充未 `await` 且传错参数类型 | 纯视觉命中可能无法绑定证据 | 不宣称每个视觉结果都已完成证据绑定 | 传 `ProductPayload` 并等待协程 |
| BM25-only chunk 在商品映射阶段可能丢失 | RRF 不是完整的两路候选并集 | 表述为关键词增强排序 | 为 BM25 命中建立独立 chunk/product 映射 |
| 文本与图片结果仅“文本优先 + 追加” | 没有真正按统一分数融合 | 不说“多模态分数融合” | 做归一化加权融合或学习排序 |
| Rerank 没有正式 fallback | Provider 失败会中断检索 | 明确关键模型依赖边界 | 增加确定性粗排降级并记录 fallback |
| 缓存 Key 不含 `top_n` | 不同返回数量可能复用错误结果 | 说明缓存是进程内优化，不是强一致能力 | 将 `top_n`、索引/数据版本加入 Key |
| 流式价格校验发生在部分文本发送后 | 已发出的错误 token 无法撤回 | 表述为分层降低幻觉，不承诺绝对消除 | 先生成缓冲段并校验，或设计纠错事件 |
| `/health` 只验证进程存活 | 健康不等于依赖可用 | 不把它称为完整 readiness | 增加 DB、索引和 provider 检查 |
| 默认测试跳过部分集成用例 | 单测通过不能证明真实外部链路可用 | 同时展示 mock 测试与 live smoke | CI 增加 PostgreSQL + provider 契约测试 |
| `STRICT_RUNTIME` 只被读取和展示 | 当前没有统一控制业务 fallback | 把它称为尚未完全接线的严格模式配置，不说开关已保护所有 live 语义 | 让各关键 Service 统一消费运行模式策略，并增加开关行为测试 |
| 数据库升级依赖 `create_all + ADD COLUMN` | 缺少版本历史、回滚、改名和数据迁移能力 | 说明它满足比赛 Demo 初始化，不是成熟生产迁移 | 引入 Alembic，并将迁移从应用启动生命周期中分离 |

### 14.5 面对评委追问缺陷，应该怎么回答？

推荐使用四句话：

1. **先承认事实**：“我们复核提交版本后确认这里存在参数契约不一致。”
2. **说明边界**：“它影响的是某条检索/图片/提示分支，不等于整个架构设计不存在。”
3. **解释根因**：“Service DTO 与 Repo DTO 演进后没有同步，且现有测试没有覆盖真实组合路径。”
4. **给出修复与防复发方案**：“统一 DTO、增加类型检查和 PostgreSQL 集成测试，并用 smoke 覆盖提交前主链路。”

不要回答“比赛时肯定没问题”“测试都过了所以不可能报错”，也不要把尚未实现的改进说成当前能力。

## 十五、课题说明会官方 Q&A

### 15.1 必须 iOS 和 Android 都做吗？

不需要。选择 iOS 或 Android 任一平台即可，重点是实现原生体验，不接受纯 Web/H5 方案。

### 15.2 50-100 条数据够吗？RAG 效果会不会很差？

本课题重点考察工程能力而非数据量。50-100 条足以验证 RAG 链路的正确性，建议精心设计数据覆盖不同类目和场景。

### 15.3 可以使用 AI 开发吗？

可以。鼓励使用 AI 开发，但需要主导架构设计并了解代码实现原理和细节。答辩时需能解释链路和代码中的细节。

### 15.4 可以用 LangChain / LlamaIndex 等框架吗？

可以。但需要理解框架内部原理。
